# 模型上下文协议（MCP）：面向开发者的全面介绍

> 来源：Stytch 博客（2025-03-28，作者 Reed McGinley-Stempel），课程 Week 2 阅读

## 执行摘要

模型上下文协议（Model Context Protocol, MCP）是一个开放标准，连接 AI 模型与外部数据和服务，让大语言模型（LLM）能以一致、安全的方式发出结构化的 API 调用。本文介绍 MCP、说明它对连接 AI 系统的价值、把它与 ChatGPT 插件、手工 API 集成等既有方法对比，并深入其最近对基于 OAuth 认证的支持。我们还会看一点代码，亲眼见识 MCP 如何工作。

MCP 充当 AI 工具与外部服务之间的**通用适配器**，省去为每个工具或 API 编写定制集成代码的麻烦。很像 USB-C 简化了多种设备的连接，MCP 为 AI 模型提供了一种统一的方法来调用外部函数、取回数据或使用预定义提示词。其核心是：MCP 提供一个接口，连接许多不同系统。

## 什么是 MCP？

MCP 本质上是一个位于 AI 应用与外部工具或数据源之间的通用适配器。它定义了一个通用协议（构建在 JSON-RPC 2.0 之上），让 AI 助手能以结构化方式调用函数、获取数据、或使用来自外部服务的预定义提示词。不必让每个 LLM 应用为每个 API 或数据库写定制代码，MCP 为所有交互提供了一种标准化的"语言"。

MCP 层让 AI 应用能安全地访问并与外部数据源和工具交互。它充当大语言模型（LLM）与各种数据库、应用或 API 之间的桥梁，无需大量定制编码即可实现无缝集成与功能。

MCP 用客户端-服务器架构来实现这一点。AI 驱动的应用（如聊天机器人、IDE 助手或智能体）作为**宿主**并运行一个 **MCP 客户端**组件，而每个外部集成则作为 **MCP 服务器**运行。服务器通过 MCP 协议暴露能力（如函数、数据资源或提示词模板），客户端连接它以使用这些能力。这种分离意味着 AI 模型不直接与 API 对话，而是经过 MCP 客户端/服务器的握手来组织交换。

## 为什么 MCP 有价值

在传统设置里，把 AI 模型连接到外部数据或动作既繁琐又零散。开发者往往要为你想让模型使用的每个 API 或数据库写一次性集成，分别处理不同的认证、数据格式和错误处理。MCP 通过标准化这些交互改变了游戏规则。主要好处包括：

- **快速工具集成**：有了 MCP，无需逐个从头定制编码，就能接入新能力。如果存在针对 Google Drive 或某个 SQL 数据库的 MCP 服务器，任何兼容 MCP 的 AI 应用都能连接它、立即获得该能力。这对自动化是巨大胜利——AI 智能体只需添加相应服务器，就能按需获取文档、查询数据库或调用 API。就像有一个"说同一种语言"的现成插件库。MCP 服务器是轻量级程序，通过标准化协议暴露特定能力，充当 Cursor 与各种外部工具或数据源之间的中介。
- **自主智能体**：MCP 赋能更自主的 AI 行为。智能体不再局限于内置知识，能在多步工作流中主动取回信息或执行动作。例如，一个高级智能体可能用 MCP 从 CRM 收集数据、再通过通讯工具发邮件、再在数据库中记录——全在一条无缝链中完成。通过实现流畅、有上下文感知、多步的交互，MCP 帮助 AI 智能体更接近真正的自主任务执行。正如一位观察者所说，MCP 通过给 AI 标准化地访问现实工具和数据，把它从孤立的"大脑"变成了多才多艺的"执行者"。
- **减少摩擦与配置**：因为 MCP 是通用接口，开发者避免了维护零散集成的碎片化。应用一旦支持 MCP，就能通过单一机制连接任意数量的服务。这大幅减少了每次让 AI 用新 API 时所需的手工配置。团队可以专注于更高层的逻辑，而不是第 10 次重写连接代码。正如 Anthropic 所说，MCP 用更简单、更可靠的单一数据访问协议取代了碎片化的集成。
- **一致性与互操作性**：MCP 在所有工具间强制一致"请求/响应"格式。这意味着你的 AI 应用不必处理"服务 A 返回一种 HTTP 响应、服务 B 返回另一种 XML"等混乱。模型的输出（函数调用）和工具结果都通过统一的 JSON 结构传递。这种一致性让它更容易调试和扩展，也让你的集成逻辑面向未来——即便切换底层模型厂商，MCP 到工具的接口保持不变。
- **双向上下文**：与简单 API 调用不同，MCP 支持在模型与工具之间维持上下文和持续对话。MCP 服务器除工具外，还能提供 Prompts（针对特定任务的预定义提示词模板）和 Resources（如文档等数据上下文）。这意味着 AI 不仅能"调用 API"，还能摄取参考数据、或遵循服务器引导的复杂工作流。协议设计之初就支持丰富交互，而非一次性查询。这在编码助手（AI 通过 MCP 与开发环境迭代）或需要与多数据源来回互动的复杂决策任务中尤其有用。

简言之，MCP 为增强 LLM 带来可扩展、即插即用的方法。它让 AI 系统能安全地接入所需的"实时"数据和动作，无需每个开发者重复造轮子。MCP 的早期采用者已为 Google Drive、Slack、GitHub、数据库等工具构建了服务器——展示了 AI 智能体如何用 MCP 与企业内容库、DevOps 工具及其他现实系统协作。

## MCP 架构——一目了然

### 客户端-服务器结构

MCP 遵循清晰的客户端-服务器架构：
- **MCP 客户端**：内嵌于 AI 应用（聊天机器人、IDE 助手、自动化智能体）。
- **MCP 服务器**：暴露外部能力，如函数（工具）、资源（数据）和提示词（模板）。

所有交互都通过标准化的 JSON-RPC 消息进行，维持安全、结构化的交换。例如，要列出可用工具，MCP 客户端发送类似这样的请求：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
```

服务器会回复一个结构化 JSON，列出工具（每个工具带名称、描述和输入 schema）。例如，服务器可能公布一个 `get_weather` 工具，并描述它需要什么输入：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [
    { "name": "get_weather", "description": "Retrieves weather data.", "schema": { "location": "string" } }
  ]
}
```

之后，当 LLM 决定用某个工具时，客户端发出调用。MCP 服务器执行该函数，并以结构化 JSON 响应返回结果。MCP 客户端（在宿主应用内）再把结果回填进模型的下文或响应。实践中，宿主应用充当媒介：它把 LLM 的意图（通常通过模型的函数调用输出）翻译成 MCP 请求，再把服务器的结构化结果传回 LLM。这种双向交换是安全、受控的——模型只能调用服务器暴露的特定工具，所有进出数据都走定义好的协议。

## 构建与部署 MCP 服务器

构建和部署 MCP 服务器是利用 MCP 做 AI 集成的关键一步。MCP 服务器充当 AI 模型与外部数据源或工具之间的中介，实现无缝通信与数据交换。MCP 一个突出特点是服务器开发的灵活性：开发者可以使用任何"能向 stdout 打印或能提供 HTTP 端点"的编程语言，从而选择偏好的语言和技术栈。

构建 MCP 服务器时，考虑架构与设计至关重要。MCP 采用客户端-服务器架构，宿主应用可连接多台服务器。这种架构带来可扩展性与灵活性，让开发者能设计处理各种任务和功能的 MCP 服务器，如数据处理、工具集成或 AI 模型管理。

部署 MCP 服务器可在多种环境进行，包括本地开发环境、云平台或本地（on-premises）基础设施。例如，Cloudflare 为构建和部署远程 MCP 服务器提供了健壮平台，让管理和扩展 MCP 部署更容易。这种灵活性确保 MCP 服务器能针对不同应用和环境的具体需求定制——无论是用于开发的本地配置，还是用于生产环境的云方案。

## MCP 客户端与工具

MCP 客户端和工具是 MCP 生态系统的核心组件。MCP 客户端是连接 MCP 服务器以访问外部数据源或工具的应用，可用 Python、JavaScript 或 Java 等多种语言和框架构建，给开发者选择最适合的工具的灵活性。

MCP 工具则是为 MCP 客户端提供特定能力或功能的软件组件。它们可与 MCP 服务器集成，实现数据处理、AI 模型管理或工具集成等功能。MCP 工具的例子包括 Claude Desktop（提供与 AI 模型交互的聊天界面）和 Cursor（提供扩展 AI 能力的插件系统）。

开发者可以构建自定义 MCP 客户端和工具来满足特定用例或需求。这种灵活性促进 MCP 生态系统的创新与实验，让开发者能创造新颖有趣的应用。无论是数据分析的专用工具，还是集成多台 MCP 服务器的客户端应用，可能性都很大。

## MCP 与其他方法对比

| 维度 | MCP | 定制集成 | ChatGPT 插件 | LangChain 等框架 |
|---|---|---|---|---|
| 集成速度 | ✅ 快速、即插即用 | ❌ 慢、定制代码 | ⚠️ 中等、专有 | ⚠️ 中等、定制代码 |
| 认证 | ✅ OAuth 标准 | ❌ 手工 API 密钥 | ⚠️ 插件专属 OAuth | ❌ 因实现而异 |
| 交互类型 | ✅ 持续、上下文丰富 | ❌ 临时性交互 | ❌ 单次交互 | ⚠️ 上下文受限 |
| 开放标准 | ✅ 是 | ❌ 否 | ❌ 否 | ⚠️ 依赖框架 |

比较 MCP 之前或与之并存的一些方法：

- **定制集成与 API 密钥管理**：最常见的传统做法，是为每个服务写定制代码，并把凭据（API 密钥或 token）交给 LLM 使用。例如写个 Python 函数查询 API、让 LLM 能调用它、在后端手工管理 API 密钥。这种方法劳动密集且不可扩展——每个新数据源都要新代码，每个环境都必须安全管理 API 密钥。由于每次集成都是独一无二的，往往导致脆弱系统。相比之下，MCP 集中并标准化了这些交互：AI 智能体只需处理 MCP 协议，任何（面向任何服务的）MCP 服务器都能即插即用；新增服务器完全不用改客户端代码。而且 MCP 为认证提供了正式结构（后文详述），让"把 API 密钥交给 AI"不再临时而为，而是走安全协议。
- **ChatGPT 插件（OpenAI Plugins）**：2023 年 OpenAI 为 ChatGPT 引入插件系统，允许模型调用由 OpenAPI spec 定义的外部 API。这是迈向标准化工具使用的早期一步，但有局限：每个插件本质上都是自己的迷你集成（有自己的 API schema 和认证），需单独构建/托管；只有特定平台（如 ChatGPT 或 Bing Chat）能用它们，因为是专有方案。插件大多也是单次调用——模型调用 API 拿信息，没有持续连接或持续交换。MCP 不同之处在于它开放、通用（不绑某个供应商或界面），支持丰富的双向交互和持续上下文。可以把 ChatGPT 插件想成封闭工具箱里的专用工具，而 MCP 是任何开发者或 AI 平台都能用的开放标准工具包。MCP 标准化的认证（尤其 OAuth）还意味着它能比 ChatGPT 系统里"插件各自 OAuth 流"更统一地处理对用户数据的安全访问。总之，ChatGPT 插件展示了标准化 LLM API 访问的价值，但 MCP 通过把它变成开放协议、并在 AI 与服务间启用持久"对话"，走得更远。
- **LLM 工具框架（LangChain、智能体库）**：在 MCP 之前，许多开发者用 LangChain 等框架给模型工具。这些方案里，你定义一组工具函数（带描述）和智能体的提示逻辑，让 LLM 决定是否使用。这能工作，但每个工具后台仍需定制实现——LangChain 最终在其库中维护了数百个工具集成。本质上，LangChain 提供了面向开发者端的标准（Python 类接口），把工具集成进智能体代码库，但没给"模型在运行时动态发现新工具"提供什么。MCP 与这些框架互补，把标准化转向面向模型端。有了 MCP，智能体可以发现自己代码里之前并未显式包含的任何 MCP 服务器提供的工具。事实上，LangChain 已增加支持，把 MCP 服务器当作又一种工具来源——用 LangChain 构建的智能体可以轻松调用 MCP 工具，利用不断增长的 MCP 服务器生态。区别在于，MCP 通过协议（JSON-RPC，带元数据等）把接口正式化，更容易接入不同环境，而不仅是 Python 框架。同样，OpenAI 原生的函数调用特性可视为处理函数调用的"格式化"（模型输出一个 JSON 函数调用），而 MCP 以标准化方式处理该调用的"执行"。OpenAI 函数调用与 MCP 往往协同工作：LLM 产出结构化调用，MCP 客户端/服务器执行并返回结果，共同实现无缝工具使用。

本质上，MCP 不是连接 LLM 与外部 API 的第一次尝试——但它从这些过往方法（插件、工具库等）中学习，统一了解决方案。它提供了开放、与模型无关的协议，简化了集成与认证。尤其在安全与认证上，MCP 的设计（含 OAuth 支持）避免了"逐插件密钥"的拼凑、或把原始 API 密钥交给模型。相反，认证可在协议内以一致、标准化的流程处理——相比现状是重大进步。

## MCP 实战：技术深潜

我们逐步走一遍典型的 MCP 交互，并看一点代码。设想一个 AI 助手想使用一个提供一组工具的 MCP 服务器（例如，针对一个假想的 "Neon" 数据库服务）。高层流程是：

1. **连接 MCP 服务器**——宿主应用（AI 助手）初始化 MCP 客户端，与服务器建立连接。视服务器位置，可通过本地进程（stdio）或远程 HTTP 流（SSE）。底层，客户端发送 initialize 消息，握手协议版本与能力。
2. **发现可用工具/资源**——客户端随后查询服务器提供什么。如前所示，它可能发送 `{"method": "tools/list"}`，取回工具定义列表。助手可用此信息告知 LLM（例如把工具列表放进系统提示词，或通过模型的函数 schema）。使用 SDK，这可能只是一行代码，如：

```js
const tools = await mcpClient.request({ method: 'tools/list' }, ListToolsResultSchema);
```

返回结构化的工具列表。每个工具条目带名称、描述和输入 JSON schema，让 AI 知道自己能做什么。

3. **LLM 选择工具**——当用户问了需要外部动作的问题，LLM 决定（常通过提示工程或函数调用能力）该用某个工具。例如用户问："AAPL 股票最新价是多少？"LLM 看到应调用 `get_current_stock_price(company="AAPL", format="USD")`。宿主应用捕获该意图（如 OpenAI 函数调用 API 会返回 JSON 形式的函数名和参数）。
4. **通过 MCP 调用工具**——客户端随即向服务器发送 `tools/call` 请求，带所选工具名和参数。用 SDK，代码大致如下：

```js
const result = await mcpClient.request({
  method: 'tools/call',
  params: { name: toolName, arguments: toolArgs }
}, CallToolResultSchema);
```

这会让服务器在它那侧执行工具的处理函数。服务器可能调用外部 API、执行数据库查询，或该工具封装的任何逻辑。结果（可能是简单值或复杂 JSON 对象）通过 MCP 响应的 result 字段返回。

5. **把结果返回给 LLM**——MCP 客户端收到工具输出，宿主应用把它整合回 AI 的响应。在许多智能体设置中，模式是：把结果注入对话、让模型继续。例如助手随后呈现："AAPL 当前股价为 $173.22（USD）。"如果用自动化循环，可以把结果给模型（或许作为系统消息追加进对话，如"get_current_stock_price 的结果：……"），模型带着该信息继续回答用户。

下面是"调用工具并在对话中使用结果"的简化示意（用原生支持工具使用的 Anthropic Claude）：

```js
// 1. 带可用工具上下文，把用户提示词发给 LLM
const response = await anthropicClient.complete({
  prompt: "User: Can you list my projects?\nAssistant: ",
  model: "claude-3.5",
  tools: tools // MCP 服务器来的工具列表
});
for (const msg of response.messages) {
  if (msg.type === 'tool_use') {
    // 2. LLM 决定使用某个工具
    const { name, args } = msg;
    // 3. 通过 MCP 调用工具
    const toolRes = await mcpClient.request({ method: 'tools/call', params: { name, arguments: args } });
    // 4. 注入工具结果并让 LLM 继续
    await anthropicClient.send({ role: 'system', content: `Tool result: ${toolRes.result}` });
  } else {
    // 5. 处理正常 LLM 回复（工具结果通常已整合）
    console.log("Assistant:", msg.content);
  }
}
```

现实中框架会为你处理很多这类事，但上述伪代码勾勒了 MCP 如何融入循环。关键是：MCP 为工具执行提供了标准化的"调用/响应"层，AI 智能体代码可以挂接上去。无论你用 OpenAI、Anthropic 还是别的 LLM，MCP 保持不变——它是模型意图与外部动作之间的胶水。

使用 MCP，开发者得到清晰、结构化的管道来扩展 AI 能力。代码更易维护（因为你调用的是通用的 `mcpClient.request`，而非各处的服务特定代码），AI 也更强大（因为它能接入任何 MCP 连接的服务）。调试也更容易——你可以监控 JSON-RPC 消息，精确看到请求了什么、返回了什么，而不用从模型生成的文本里找线索。

## 早期局限（无内置认证）

当 MCP 刚出现（2024 年底）时，它提供了工具与数据交换的核心协议，但缺少连接远程服务器的标准化认证机制。实践中，早期 MCP 演示和实现往往要求把 MCP 服务器运行在本地或可信环境里，那里认证不是大问题（因为 AI 和服务器在同一台机器上）。例如，开发者可以在 localhost 上用预先获取的 token 运行一个面向 Google Drive 的 MCP 服务器，再把 AI 应用指向它。但跨互联网、或与第三方服务使用 MCP，在没有正式认证流程的情况下很棘手。

许多初始 MCP 服务器假定用户会在启动时手工提供凭据或 API 密钥。例如 Anthropic 的 quickstart 建议通过配置或命令行提供自己的凭据（API 密钥、token）来运行预制服务器。这意味着服务器本身能访问你的密钥，MCP 客户端只是信任那台服务器。这对个人或单用户场景可行，但对多用户应用或云端托管的智能体无法很好扩展。没有一个标准握手让 AI 智能体说："嘿，我被允许代表用户 X 访问这个服务，这是我的凭据。"

本质上，早期 MCP 客户端除带外方式（如预共享 token 或干脆无认证运行）外，没有途径向 MCP 服务器认证。这是一个显著局限——MCP 被设计为开放、基于互联网，但缺少认证标准，安全的远程使用受阻。

认证标准缺失意味着 MCP 客户端无法自行安全连接到任意服务器。你要么把客户端 ID/API 密钥硬编码进客户端（在分布式应用里不理想），要么无认证运行、假定只有授权用户能访问服务器（通常靠保持本地）。显然，要让 MCP 充分发挥潜力（如把 AI 智能体安全连接到云端托管的数数据源），需要更好的方案。好消息是社区认识到了这一点，并已着手把基于 OAuth 的认证融入 MCP。

### OAuth 2.0 认证流程

为弥补初始认证局限、增强安全连接，MCP 采用了 **OAuth 2.0**——一个广受认可、健壮的认证标准。OAuth 2.0 提供了安全、可扩展的框架，让 MCP 客户端能与远程服务器、云端托管资源和多用户环境安全交互。把 OAuth 2.0 集成进 MCP 的关键组成部分与好处包括：

- **动态客户端注册（DCR）**：MCP 支持动态客户端注册，让客户端自动向 OAuth 服务器注册。这免去了手工客户端配置或硬编码凭据，大幅简化了开发者的部署。
- **自动端点发现**：MCP 利用标准化的元数据 URL（遵循 OAuth 的发现协议），让客户端自动发现 OAuth 端点。这减少了配置开销，让 MCP 部署更简单、更灵活。
- **安全的授权与 token 管理**：客户端安全地获取精确匹配用户权限和访问范围的 OAuth token。这确保客户端只访问用户明确允许的资源，提升安全与合规，尤其在多用户和云环境里。
- **可扩展且安全的多用户支持**：OAuth 2.0 的设计天然支持多个并发用户和服务，解决了 MCP 早期的一个显著局限。应用现在能为大量用户无缝处理授权流程，这对广泛的云采用至关重要。

## 调试与故障排查

调试与故障排查是处理 MCP 服务器和客户端时的关键环节。MCP 提供多种工具和技术用于调试与排查，确保开发者能高效定位并解决问题。其中一个关键工具是 **MCP Inspector**——面向 MCP 服务器的交互式调试工具。

MCP Inspector 让开发者测试和检查 MCP 服务器，发现并解决 MCP 服务器集成的问题。它提供 MCP 客户端与服务器之间交互的详细视图，更容易定位问题、理解根本原因。此外，MCP 提供一份全面的调试指南，列出常见问题与解决方案，帮助开发者快速排查并解决问题。

调试 MCP 服务器时，考虑系统的架构与设计至关重要。开发者应定位出问题的具体组件或模块，用 MCP Inspector 等工具诊断并解决。通过系统化的调试方法并善用可用工具，开发者能确保他们的 MCP 集成健壮可靠。
