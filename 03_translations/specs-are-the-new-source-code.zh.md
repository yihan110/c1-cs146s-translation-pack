# 规格说明已死，规格说明万岁！（The Spec Is Dead, Long Live the Spec!）

> 来源：Ravi on Product（Ravi Mehta 与 Danny Martinez，2025-07-31），课程 Week 3 阅读
> 副标题：原型是新的规格说明，而规格说明是新的……源代码？

在我的职业生涯里，规格说明（spec）越写越短。我初到微软时，PM 的价值以"他们的规格说明的重量"来衡量。多年后，在 Tripadvisor，我们津津乐道那位把"写在餐巾纸上的规格说明"带到产品评审会的 PM。

产品团队常把规格说明当作"文书工作"——在"真正的发布工作"之前一个必要的麻烦。工程师因优雅的代码被称赞，设计师因漂亮的 UX 被赞美，PM 因带来影响而受表扬。但规格说明？它们通常被草草带过、随手丢弃、遗忘。

这从来都是个错误。在我的《产品能力工具包》里，**功能规格说明（Feature Specification）排在十二项能力之首**，是有原因的。它支撑着产品执行，连同产品交付与产品质量。完美的执行是好产品管理的基础，而一份出色的规格说明是起点。

今天，我们的构建方式正在转变。工程师变得快得多——快很多。AI 能在几分钟内把粗略想法变成可运行的代码。瓶颈不再是"构建"。而是**"知道该构建什么，并让团队围绕这些需求对齐"**。于是，不起眼的规格说明不再是转瞬即逝的文书。它是产品管理的基础——**它正成为源代码本身**。

## 为什么 PM 突然成了瓶颈

Andrew Ng 在近期的演讲《用 AI 更快构建》中指出一个前所未有的趋势：

> "这是我一生中第一次看到有经理向我提议，PM 的数量是工程师的两倍。我仍不确定这个提议好不好，但我认为它标志着世界正走向何方。"——Andrew Ng

这印证了我们上一篇的预测：随着工程师借助 AI 以许多倍的速度交付，公司需要**更多** PM 来支持那些高效的工程师，而非更少。产品交付加速后，对产品管理的其他每个方面——理解客户需求、设计正确的功能、验证影响——都产生了巨大压力。而所有这些压力都汇聚到一个产物上——**规格说明**。

## 规格说明——新的源代码

在传统软件开发里，程序员编写人类可读的"源代码"，它被编译成高度优化的机器可读"目标代码"。目标代码（也叫二进制）是可从源代码重新生成的副产品。**源代码是真正的事实来源**。

OpenAI 的 Sean Grove 有一个挑衅性的论点。在他近期演讲《新代码》里，他主张：**一份写得很好的提示词（即规格说明）就是新的源代码**。照此看来，我们做 AI 开发是反着来的——我们精心构造提示词向模型传达意图，AI 生成代码，然后我们保留代码、扔掉提示词。

Grove 评论道："这感觉就像你撕碎了源代码，然后极其小心地对二进制做版本控制。"想想看：传统编程里，源代码是神圣的——它包含注释、结构、文档，是理解和修改系统所需的一切；二进制只是下游产物。但用 AI，我们把这个关系颠倒了：我们把生成的代码当作值得保留的产物，把规格说明——提示词——当作可抛弃的。

Grove 认为这完全弄反了。代码，哪怕是优雅的代码，也是他所称的"来自规格说明的有损投影（lossy projection）"。就像反编译二进制得不到原始注释和变量名，读代码也看不出其背后的完整意图。**而规格说明包含了一切**。一份足够健壮的规格说明能生成"优秀的 TypeScript、优秀的 Rust、服务器、客户端、文档、教程、博客文章，甚至播客"。

更重要的是，规格说明做到了代码做不到的事：**它让人类和机器在共同目标上对齐**。Grove 说得简单直接："一份书面规格说明能有效地对齐人类，它是你用来沟通、讨论、争辩、引用和同步的产物。"他预言："在不久的将来，沟通最有效的人就是最有价值的程序员。而且说白了，如果你能有效沟通，你就能编程。"新的稀缺技能不是编码，而是**写出能完整捕捉意图和价值的规格说明**。对产品经理来说，这应该耳熟——我们一直在做这件事，只是如今机器也在听了。

## 等等，原型不是杀了规格说明吗？

直到不久前，产品生命周期仍须从规格说明（或 PRD、概念文档、餐巾纸）开始，它启动了最初的线框、设计、原型和 MVP 开发。传统方法感觉像个必要的麻烦：工程师构建基本 MVP，把某个东西——任何东西——交到客户手里。"如果你不为第一版产品感到难堪，那你发布得太晚了"成了信条。

我们的整个产品构建方式近来发生了重大转变，在这个新世界里，**规格说明往往是输出，而非输入**。如今，你不必发布一行代码，也能把原型交到客户手里。v0、Lovable、Replit 等工具让你在数小时内（而非数周）构建出可用的原型，无需任何工程能力。这不仅是更快——而是根本性的不同。手持一个"vibe coded"的原型，你可以在写一行功能规格之前就收集真实客户反馈，测试假设、迭代流程、打磨交互。

- 旧工作流长这样：模糊想法 → 线框 → 设计 → 工程师构建的 MVP → 客户反馈 → 痛苦的规格修订 → 线框 → 设计 → 重建 → 祈祷。
- 新工作流：模糊想法 → 快速原型 → 客户反馈 → 极其清晰的规格 → AI 辅助实现。

**原型没有杀死规格说明。它们在让规格说明变得更好。**

## 规格驱动开发的实战

我们看一个实战例子。Danny Martinez 是 decimals 的创始人，一个（尚在隐身）平台，让创作者经济里的专家把自己人脉中的候选人安排到岗位上。Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来两个影响：(1) 大幅改善了大功能与工程的沟通；(2) 让毫无编码经验的 Danny，能从小东西一路从详细规格做到上线功能。以下是 Danny 的口述：

> 我最近做的一个例子。背景：我们在构建一个让专家型网红把候选人从人脉中安排到岗位的产品。发布了一个新落地页后，我们需要给专家一个快速访问自己页面链接的方式。

这是来自我联合创始人的一条消息，指一个需要上线的简单按钮：

> "我们需要页头里一个跳到公司申请页的按钮。我现在正专注于邮件。如果你能接下，这个 vibe-code 就能搞定。"

够简单，正是那种现在非技术人员自己就能交付的东西。以下是让它几分钟内上线的设置与步骤：
- 项目管理工具：Linear
- IDE：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP 服务器：Linear MCP server（让 Copilot 能访问 Linear 工单）

过程中的步骤（可对照上方 Loom 视频）：
1. 从联合创始人的 Slack 消息生成一个 Linear 工单；
2. 在工单里澄清我要的新文案是什么；
3. 打开 Copilot，提示 Claude 打开 Linear 工单；
4. 提示 Claude 评审工单、并结合代码库分析；
5. 提示 Claude 创建分支并实现这些改动；
6. 测试改动，确保如预期工作；
7. 在 GitHub 上打开一个 pull request（PR）把改动合入代码库；
8. 等工程师评审/批准 PR。

放大看，这套配置的真正力量清晰浮现。是的，这是个琐碎的例子，但重点是：**一个非技术人员如今只需通过 GitHub Copilot 给 Claude 几条提示，就能在 Linear 工单、代码库和工程师之间来回**。而这一切的关键部分仍然不是代码本身——是规格说明。

现在，要让它顺利工作，有必要说明所需的前提条件：
- **要具体（Being specific）**：用含糊的规格只会得到一团糟的代码库。让 Claude 先起草工单初稿、评审代码库、帮它变得更具体，是流程里必不可少的一环。在我们这里，还有一份"写好规格的指南"。
- **要有选择（Being selective）**：上述方式最适合更简单的任务。工单越复杂，就越需要懂行的人介入（在这些情况下，"自助"到头来一点也不自助）。
- **要设门禁（Gatekeeping）**：这套方式之所以有效，正因为有一位懂行的真正工程师在评审改动、确保"简洁性与功能性"之间的平衡。

但要说清楚：**规则已经变了。规格说明是每个构建产品之人的事实来源，包括 LLM 在内。** 有了合适配置，一个非技术人员为代码库做贡献是完全现实可期的。只要有足够的时间和耐心，你可以开始自己理解代码库、自己实现改动，而不是每次都单纯依赖 Claude 救场。总有一天，你甚至可能一边啜着咖啡，一边等一个 AI 智能体替你上线工单。

如果你是 PM，担心 AI 会对你的工作做什么——关键是认识到**工作本身正在改变**。但这对其他人也一样。好的一面是，杰出 PM 所需的核心技能在这个新世界里更加宝贵。正如我们上一篇所预测，以这种方式工作的公司将需要更多、而非更少的 PM。而事实证明，那个预测相当灵验。

## 规格说明万岁！

发明"赛博空间"一词的科幻作家 William Gibson 曾说过："**未来已经到来——只是分布得还不均匀。**"想到 AI 的能与不能时，我就想起这句话。今天，AI 的收益极不均匀。有些事——生成代码、文本、图像——已实现量子跃迁，以 AI 速度运行；另一些事——与客户交谈、发现他们的需求、说服他们购买——仍以人类速度前进。

这种不均匀的分布正在重塑产品团队。聚光灯正从"实现工作"转向"理解工作"。那些一直让最佳 PM 脱颖而出的核心技能——理解用户需求、清晰定义问题、设计优雅解决方案——已经呈指数级升值。**最好的 PM 把这些洞察变成规格说明——在日益自动化的开发世界里，它们对齐团队、指导实现，并作为持久产物留存。**
