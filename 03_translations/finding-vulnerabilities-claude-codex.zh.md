# 用 Claude Code 和 OpenAI Codex 在现代 Web 应用中发现漏洞

> 来源：Semgrep 安全研究（2025-09-02，Romain Gaucher、Vasilii Ermilov、Clint Gibler），课程 Week 8 阅读

我们深入研究了 AI 编码智能体发现漏洞的能力，揭示了出人意料的强项、关键的弱点，以及一个严重的**一致性问题**。

**TL;DR**：我们评估了 AI 编码智能体在真实代码中发现漏洞的有效性。
- **方法**：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且大型的开源 Python Web 应用中找漏洞。它们共同产生了 **400 多个安全发现**，由我们的安全研究团队评审。
- **AI 编码智能体确实能找到真实漏洞**：Claude Code 找到 46 个漏洞（14% 真阳率 TPR、86% 假阳率 FPR），Codex 报告 21 个漏洞（18% TPR、82% FPR）。其中约 20 个是高严重性漏洞。
- **AI 理解上下文、却卡在数据流上**：Claude Code 最擅长找不安全的直接对象引用（IDOR）bug，真阳率 22%（59 个报告里 13 个正确）；但跨多个文件和函数做污点跟踪很吃力，SQL 注入真阳率 5%（2/38）、XSS 真阳率 16%（12/74）。OpenAI Codex 报告任何正确的 IDOR 都很吃力（真阳率 0%，0/5），SQL 注入（0/5）和 XSS（0/28）也很差，但令人惊讶地比 Claude Code 报告了更多正确的路径遍历问题（真阳率 47%，8/17）。
- **非确定性是真实困扰**：对完全相同的代码库运行完全相同的提示词，多次结果往往截然不同。在某个应用中，三次相同运行分别产生 3、6、然后 11 个不同发现。

**关键要点**：
- 用相对简单的、安全聚焦的提示词，AI 编码智能体**已经能在真实应用里找到真实漏洞**。
- 但根据漏洞类别，结果可能相当嘈杂（高假阳率），尤其对 SQL 注入、XSS、SSRF 这类传统注入式漏洞类别。
- 详细的评估和基准测试，是理解"某方法在找漏洞上多有效"的关键（这一点一直成立，面对 LLM 这种非确定性工具更是如此），也能知道你的改进方向是否正确。

这是我们"使用和增强 AI 找漏洞"系列的**第一篇**。本篇涵盖：常见 SAST 基准的问题及其如何影响 AI SAST 评估；关于基于 AI 的漏洞狩猎的一些开放研究问题；我们的 AI 编码智能体实验、数据集和所学；Anthropic 的 `/security-review` 命令为什么很平庸；AI 编码智能体的非确定性及其成因。

## 引言

在 Semgrep，我们以应用安全（AppSec）为生。我们很早就把 AI 产品化（Assistant 背后的技术、用 promptfoo 测试 AI 工作流、用安全研究员分诊评估自动分诊性能），不断研究"传统确定性分析与现代 AI 上下文能力"的最佳组合，而不仅仅是追逐潮流。这项研究是那个持续使命的一部分。我们正开展一次深入的、公开的探索，来回答每个人都在想的问题：**LLM 在源代码中找漏洞到底有多有效？**

## 关于基于 AI 的漏洞狩猎的开放研究问题

为引导调查，我们把"LLM 擅长找 bug 吗？"这个宽泛问题拆成更具体、可测量的子问题：
- 基于 LLM 的漏洞发现的假阳率和假阴率是多少？它是否因编程语言、框架、代码库规模或漏洞类别而异？对代码写法有什么敏感性？
- 假阳和假阴的常见原因是什么？
- 分析的确定性如何？你每次都得到相同结果吗？

对注入类漏洞，我们特别想知道：LLM 在"来源（source，如用户提供的值）到汇点（sink，如消费原始 SQL 查询的方法）之间跟踪用户输入"有多有效？它能跨函数和文件跟踪数据吗？它能推理净化函数和其他安全控制吗？它能推理来自第三方开源依赖的函数吗？

## 常见 SAST 基准的问题：缺乏真实性

在深入发现之前，先谈谈我们如何衡量 AI 性能。当前许多研究/主张依赖的基准虽然有价值，却没能完全捕捉真实世界代码的复杂度：
- **带已知漏洞的应用**：这些基准只用带已知漏洞的开源应用（很多可在 vulnerable-apps 找到）。WebGoat、JuiceShop、OWASP Benchmark 等。但有个问题：当前 LLM 很可能已摄入这些仓库的代码、以及网上许多公开文章，给了它们先验知识、扭曲了结果。它们的代码往往不真实——堆满注释、注解和直接暗示或描述漏洞位置/利用方法的变量名。有时甚至工具结果都检入了仓库。
- **XBOW**：为自动渗透测试工具提供基准，但不适配静态分析——代码往往太造作、太简单，不代表真实应用。ZeroPath 净化了一批，但只有一小部分。而且每个测试用例都是微应用，为刺激特定攻击场景而设计。若聚焦 Python 基准，XBOW 有 45 个：45 个平均不到 98 行代码、3 个 Python 文件的微应用。这太小，捕捉不了"跨整个代码库或多个函数搜索和推理"的复杂度。
- **CVE 记忆偏差**：LLM 在互联网海量公开数据上训练，包括发现并修复 CVE 的那些代码库本身。这创造了根本性的数据污染问题——AI 可能不是通过新颖分析检测漏洞，而只是认出训练时记住的模式。

最近学者设计了 CyberGym、EyeballVul、SecVulEval 等基准，它们改进很大、更接近真实示例，但缺乏对现代 Web 应用的聚焦、或把漏洞与更广泛的应用上下文隔离。EyeballVul 从开源项目抽取真实世界、经人工核实的漏洞，呈现为最小、可复现的测试用例——但基于真实代码却仍把漏洞与更广泛应用上下文隔离，使搜索问题更简单。SecVulEval 和 CyberGym 聚焦 C/C++ 漏洞，在各自领域有价值，却不适用于主导现代云原生开发的 Python/JavaScript 等 Web 中心语言。

每种方法都有用、有时该用，但它们不一定反映现代软件开发的现实。**真实应用不是干净、孤立的函数，而是依赖、框架和业务逻辑的复杂网络。**我们的方法不同：在 11 个大型、Python 基础、积极维护的开源项目上测试，用常见 Web 框架（Django、Flask、FastAPI）编写。我们的方法与前述互补，我们认为它独特在于：a) 旨在代表现实世界 AI 驱动的漏洞发现（而非小的孤立合成示例）；b) 不被模型训练数据污染；c) 代表多数开发者和公司实际在构建的应用类型——用现代语言和框架的 Web 应用。

## 本博文范围

为使其可操作，我们聚焦：用开箱即用、一条脚本化提示词的 Anthropic Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）各跑一次，请它们返回 SARIF 格式的安全问题；分析 11 个大型、真实世界的开源 Python 项目；聚焦常见、高影响的漏洞类别：认证绕过（Auth Bypass）、IDOR、路径遍历、SQL 注入、SSRF、XSS；用 Anthropic 新的 `/security-review` 命令做探索性结果；在 3 个应用上各跑 3 次，探索 IDOR 的（非）确定性。

为夯实研究，我们选流行且积极维护的项目。以下是所分析应用的规模（应用 ID 不公布，因仍在负责任披露流程中；相关数据表见原文，覆盖 7k 文件、>800k 行 Python 代码的 11 个大型应用）。

## 实验：AI vs. 真实世界应用代码

我们对 11 个应用运行分析，然后人工分诊全部 **445 个发现**，多数（尤其 IDOR 或认证绕过）做动态验证。

**Anthropic Claude Code（v1.0.32，Sonnet 4）**：

| 漏洞类别 | 真阳 | 假阳 | 真阳率 |
|---|---|---|---|
| 认证绕过 | 6 | 52 | 10% (6/58) |
| IDOR | 13 | 46 | 22% (13/59) |
| 路径遍历 | 5 | 31 | 13% (5/36) |
| SQL 注入 | 2 | 36 | 5% (2/38) |
| SSRF | 8 | 57 | 12% (8/65) |
| XSS | 12 | 62 | 16% (12/74) |

使用命令：`claude --verbose --print --output-format json --dangerously-skip-permissions <PROMPT>`

**OpenAI Codex（v0.2.0，o4-mini/high reasoning）**：

| 漏洞类别 | 真阳 | 假阳 | 真阳率 |
|---|---|---|---|
| 认证绕过 | 5 | 32 | 13% (5/37) |
| IDOR | 0 | 5 | 0% (0/5) |
| 路径遍历 | 8 | 9 | 47% (8/17) |
| SQL 注入 | 0 | 5 | 0% (0/5) |
| SSRF | 8 | 15 | 34% (8/23) |
| XSS | 0 | 28 | 0% (0/28) |

使用命令：`codex --config disable_response_storage=true --config model_reasoning_effort=high --config model_reasoning_summary=detailed exec --model o4-mini --full-auto --skip-git-repo-check <PROMPT>`

### 我们发现

- **两个工具今天都有用**：它们找到真实安全漏洞，但很嘈杂。整体噪声仍很高，但它们在流行开源 Python Web 应用里找到了真实安全漏洞。总体上 Claude Code 找到 46 个漏洞（14% TPR、86% FPR），Codex 报告 21 个（18% TPR、82% FPR）。
- **许多 IDOR bug 初看正确，Claude Code 还提出可信修复**：LLM 不仅能找到这些 bug，还能提可信修复——比如基于代码里现有模式注入新的权限检查。IDOR 问题难以分诊，多数我们必须测试才能确定，这让真阳率大幅降低。
- **Claude Code 是好的"安全护栏"工具吗？**：许多发现虽技术上算假阳，仍是好的"护栏"建议、或看起来像。例如模型常建议把已经安全的 SQL 查询参数化。虽非漏洞，但加固了代码。我们仍视为假阳，只是不如其他严重。**但这些代码加固建议不能总被信任。**我们找到几处（尤其客户端 JavaScript 代码）AI 试图修复它感知到的、围绕 DOM 操作的问题，实际却破坏了代码（我们观察到的案例里把 HTML 双重转义），而那里根本没有安全问题。
- **XSS 和 SQL 注入——难以把组件拼起来**：模型难以把数据从服务端框架追溯到客户端组件（XSS 常见模式）、或跨复杂应用层跟踪。它常被静态定义的数据搞糊涂，或没识别出服务端净化。
- **重复提示有助于得到更多结果**：LLM 的概率特性意味着用略有不同的方式问同一问题会得到新发现，凸显分析的不一致。在同一代码库上多次重复同一提示词得到不同答案，但最终会绕回同一批发现。
- **OpenAI Codex 有时不报告有效 SARIF**：我们预期的 66 份报告里有 9 份不是有效 SARIF。我们认为那些文件里的所有发现，但它们不是有效 SARIF 或 JSON。Claude Code 在我们试过的所有案例里都没这问题。

## 相同代码、相同 AI、每次不同的 bug：AI 编码智能体的非确定性问题

为探究非确定性如何实际表现，我们选三个应用、用相同提示词对同一安全问题（IDOR）跑多次。一个模式浮现：**AI 的发现每次运行都不同。**

在漏洞检测语境下这是个重大问题。首先，作为安全工程师，我们理想中想要比"我希望模型这次搜得够彻底"更强的保证。其次，**间歇性检测漏洞会在安全工具或漏洞管理系统里造成不一致和噪声**。例如用 SAST 平台、ASPM 或内部自建系统时，这些系统常假设"先前检测到的漏洞不再出现 = 已修复"。但 LLM 驱动的检测未必如此——单次扫描可能漏掉，后续扫描重新发现同一问题会生成"新"发现，导致重复的 JIRA 工单和开发者沮丧。

我们观察到的具体例子：PY-APP-007 第一次运行识别出"缺失搜索授权"漏洞（另两次没有）；第二次运行标记了那次运行独有的问题；第三次又找到自己一套不同的漏洞。PY-APP-006 类似：第一次运行在用户 API 里挖出一个漏洞，后续运行聚焦代码库不同部分（事件摘要和笔记模块）。PY-APP-002 的变异性最显著：识别漏洞数从第一次的 3、第二次的 6、跳到第三次的 11，每次运行呈现只有部分重叠的不同发现。

这背后是什么？我们认为关键因素是所谓的**上下文腐化（context rot）和压实（compaction）**。当 AI 智能体被派去分析整个代码库，它要处理海量信息：上下文腐化导致无法从自身上下文准确检索。为应对，LLM 使用一种有损压缩（有时叫压实），意味着函数名、路径等更精细的推理细节可能丢失在摘要过程里。就像试图总结一部又长又复杂的小说：你会抓住主要情节，但必然错过一些微妙和细节。同样，AI 可能丢失某个特定架构模式或微妙数据流，导致一次运行漏掉、另一次又抓到的漏洞。我们在 PY-APP-006 里看到清楚例子：AI 的一个修复建议不完整，因为它没能复用现有的用户授权基类——那次运行中看似丢失了这块关键上下文。

这种非确定性对"我们如何对待 AI 原生 SAST"有重要启示。一方面，AI 每次都"想得不同"的能力意味着它能探索更广范围的潜在攻击向量，很像一支视角多元的人类渗透测试团队。另一方面，它引入一定的不确定性，可能导致困惑或异常行为。
- **覆盖不完整**：单次运行可能给人虚假的安全感，因为它可能漏掉后续运行才抓到的关键漏洞。
- **缺乏可复现性**：无法复现结果，使验证 AI 发现、以一致可复现的方式信任其输出变得困难。
- **成本和时间增加**：为获得更完整图景而跑多次审计，会显著增加时间和计算资源。注意：传统软件一旦写好，基本可以"免费"重跑（不含硬件、电力等成本）。对 LLM 重度工具则不然——读取代码库并推理它，每次扫描可能花几十到几百美元的 token 成本。这个成本对当前模型可能随时间下降，但更新模型可能更贵。

## Claude Code 的新 `/security-review` 命令有多有效？

Anthropic 为 Claude Code 发布了一个新命令 `/security-review`，设计为在 pull request 上运行、检查改动文件并提问识别特定安全问题。在整个代码库上运行它时，我们发现识别的安全问题相当有限。很多时候，它找不到我们"提示 Claude Code 每次只搜一种安全问题"时得到的问题。我们在 PY-APP-003、PY-APP-002、PY-APP-008 上运行此命令，在全部三个里只找到一个 XSS——与整体实验的结果大相径庭。

## 回答我们的问题

回顾我们基于所学对最初研究问题的回答：
- **假阳/假阴率是多少？** 对真实代码上的原始 AI，假阳率非常高，从最好的 Codex 路径遍历 53%（Claude Code IDOR 78%）、到最差的 Claude Code SQL 注入 95%、Codex SQL 注入或 IDOR 100%。性能也随应用剧烈变化，从 PY-APP-002 的 100%（10/10）真实 IDOR（Claude Code）、到 PY-APP-007 的 0%（0/7）。跨所有应用和所有报告问题，Claude Code 找到 46 个漏洞（14% TPR、86% FPR），Codex 报告 21 个（18% TPR、82% FPR）。因用的是真实应用，此实验无法精确测量假阴率——我们会在后续博客介绍测量假阴率的技术。
- **它为什么失败？** 我们观察到的主要弱点，是缺乏对注入问题"代码执行"的深度语义理解。模型难以处理过程间污点流和隐式流——传统 SAST 引擎通常就是为此而建的。部分局限也来自上下文压实和上下文腐化。我们会继续更详细地探索这些局限及缓解方案。
- **脚手架和智能体工作流有多重要？** 它们不只重要，而是正变得**必不可少**。安全评审中 AI 的未来不是单一的、单体的模型，而是一个 AI 智能体系统（包括我们案例中的编码智能体），它能用工具、推理证据、协作找到并验证漏洞。虽然我们（目前）没有"用可访问 Claude Code 的智能体 vs 更典型的上下文工程（即构建脚手架提供所有相关代码）+ 推理模型"差异的数据，但我们观察到系统"处理复杂流程、在报告安全问题途中做出明智决策"的能力有巨大差异。话虽如此，Sean Heelan 通过足够上下文工程让推理模型报告漏洞（8% 的时间）就是一个反例，强烈建议读他的博客。
- **这一切的成本呢？** 不幸的是，我们没能在 Claude Code 和 Codex 之间统一跟踪成本。Claude Code 的总成本是 **$114**（用于所有这些漏洞和应用，不含非确定性和 `/security-review` 命令的运行）。

## 结论

LLM 不是明天就会取代人类安全工程师的银弹，事实上它们在端到端找高严重性注入式漏洞上相当弱。但它们是非常强大的工具。我们的研究表明：通过理解它们的强项（上下文推理）和弱项（代码的深度语义），并通过围绕它们、用先进静态分析引擎构建复杂的智能体系统，我们能创造新一代安全工具，比以往任何东西都强大得多。
