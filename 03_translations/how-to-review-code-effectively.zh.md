# 如何有效地评审代码（How to Review Code Effectively）

> 来源：GitHub 工程博客（Sarah Vessels，Staff Software Engineer，2024-07-23），课程 Week 7 阅读

作为 GitHub 的一名 staff engineer，代码评审是我日常工作的主要关注点之一。过去八年，我评审了超过 **7,000 个 pull request**。为什么这么多？因为代码评审对构建好软件至关重要——另一双眼睛往往能发现你本来会漏掉的问题。

我把代码评审看作我工作中最重要的方面之一。事实上，每当看到队友有一个可供评审的 pull request，我宁可放下手头的分支去评审他们的改动。毕竟他们的 pull request 已经通过了持续集成（CI）的考验、达到了他们自己"完成"的标准，所以很可能比我在做的半成品更接近可发布状态。我更愿意把他们的代码推到终点线，而不是再多花不知多久去磨我的代码。我越早给出反馈——"这可能是 nil 并导致错误"、"这看起来是个 n+1 查询"、"这里最好有个方法签名"——这些反馈就越快被处理，缺陷被修复、功能被上线。

我想分享我如何对待代码评审，希望我们能一起交付更好的代码。

## 什么是代码评审？

严格说，代码评审——通过 GitHub 上的 pull request 评审——允许协作者对 pull request 中提出的改动发表评论、表示批准、或在合并前要求进一步修改。我把一个 pull request 看作一段对话的开始。我把它读作作者在说"我认为这改进了我们今天的现状"。代码评审是塑造产品实现的大好机会。作为评审人，我的工作是和作者来回讨论，通过提问、质疑假设、通常充当第二双眼睛来改进他们的代码。

## 微调你的代码评审流程

### 如何找到待评审的 pull request

我活在 GitHub 的通知收件箱里。它是我在浏览器固定的少数几个标签之一，随时可用。任何等 CI、任务间隙、一天开始、或一般有空的时候，我都喜欢查收件箱。我评审的多数 pull request 都是在那里找到的。GitHub 的团队往往有一个当"大本营"的 Slack 频道，那是分享"可供评审" pull request 的好地方——也是我发现 pull request 的主要途径之一。我还用 GitHub Slack 集成，让某个 Slack 频道订阅与我团队相关的、新的 pull request。为过滤出现在 Slack 里的 pull request，我使用一个团队专属标签，然后在 Slack 里用 `/github subscribe your/repo pulls +label:"your-team-label"` 这样的订阅命令。

我喜欢用这样的查询搜索可能需要评审的待处理 pull request：`is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team`。用这个查询，我能找到 GitHub 组织里打开的、未归档的、非草稿、且把相关 codeowner 团队列为请求评审人的 pull request。我通常会省略 `review:required` 搜索限定符，因为即使队友已经评审过，我也乐意再看一遍——评审代码不只帮助作者，也帮我掌握自己负责代码的变化。

### 用评审人团队管理通知

你不想让代码变更惊动一个超大的团队、导致每个人默认"评审这不是我的责任"。那会造成 pull request 要么无人问津地搁置，要么在还没该合并时就被合并——因为关键评审人在通知洪流里漏掉了它们。这两种情况都影响产品质量。

我建议尽可能精简你所在的 codeowner 团队数量，让通知可控。这样，落进你收件箱的 pull request 不只是噪音，而是你确实觉得该评审的东西。大型、包罗万象的 codeowner 团队作为后备方案还行，但作为自动评审请求的第一线默认就不好了。好好组织你仓库的 `CODEOWNERS` 文件，配以定义清晰的代码边界，以限制通知、帮评审人避免"通知疲劳"。

限制团队通知的另一个办法，是创建一个"第一响应人（first responders）"团队，然后用自动化按计划添加和移除成员。这能让你的团队专注于日常代码库，同时按计划值守的第一响应人收到你团队服务区域的 pull request 通知。例如，用 PagerDuty API 判断某天谁是第一响应人，然后用 Octokit 库添加和移除团队成员。

### 用自动化跨团队标准化代码评审

仓库级配置和自动化，如使用 `CODEOWNERS` 文件和分支保护规则，有助于跨团队强制评审流程标准。其他标准——比如 pull request 里什么值得评论——必须由我们人类维护。把团队里的代码评审方式写成文档，确保任何提供评审或提交 pull request 的人都知道：如何让 pull request 被评审、评审的预期周转时间、以及用了哪些自动化辅助评审。

有些团队用项目看板跟踪进来的待评审 pull request；我看到这对一个管理共享 API 的团队很有效（该区域常被团队外的人修改）。另一些团队只依赖 GitHub 通知，当代码所有权范围严密、团队又有纪律地及时评审 pull request 时，这也行之有效。

如果你遵循一个团队专属流程，自动化可以帮助与团队外的人沟通预期。例如，如果许多其他团队依赖你的评审，你可以用一个 bot，在"请求你团队评审"的任何 pull request 上自动留一条评论，告诉作者他们什么时候能听到你的回音。

## 什么造就了好的/坏的代码评审？

好的代码评审增加清晰度，把代码推向比起点更好的状态。作为评审人，沟通清晰是关键。你要说清哪些评论是你的个人偏好、哪些是批准前的阻碍项。为你建议的方法提供例子，能提升你的评审、让意思更清楚。如果例子能来自同一个仓库，更好——那通过鼓励一致的实现进一步支持你的建议。

相反，差的代码评审缺乏清晰度。例如，没有任何评论的一揽子批准或拒绝，会让 pull request 作者怀疑评审是否彻底。哪怕只是复述你理解作者的意图，也能浮出"你和作者是否理解一致"。一个不清楚"建议应在何时实现"的评审，对作者也是糟糕的体验。注明"现有未改代码应重构"或"应处理另一个情况"没问题，但重要的是说明它们是否是批准的前提。如果 pull request 不采纳你的建议也可以落地，务必说明。保持 diff 小、把这些改动作为独立的 pull request 单独上线，可能更稳妥。

下面这条评审评论展示了具体性、并清楚传达了建议的实现方式：

> "我看到你的新方法与这个文件里现有风格一致，接收 [X] 个参数。这么多参数损害可读性，也意味着这个函数做得太多。你觉得在后续 pull request 里重构这个方法及现有方法、减少它们接受的参数数量怎么样？"

这条评论做得好的是：提供具体细节；引用具体代码或问题；建议问题的解决方案；引用证据或给出解释。

在光谱的另一端，下面是些可以更好的评审评论示例：

**"我不喜欢这个。"**——评审人不喜欢什么？他们心里有可以明说的替代方案吗？
可改进为：
- "这一行做了太多事，我们能简化它以提高可读性吗？"
- "我认为这会因 n+1 查询而有性能问题。"
- "我们能改用[偏好的框架]的方案，而不是写自定义实现吗？"

**"这样行不通。"**——为什么行不通？
可改进为：
- "这样行不通，因为 [X]，见这个相关问题：[issue 链接]。"
- "这在 [pull request 链接] 里试过，因 [X] 没成。"
- "如果你在 [X] 上遇到问题，可以试试 [替代方法]。"

**"我认为这修复了一个 bug。"**——我喜欢这种指出，但有更多上下文（如 issue 链接）能让它更清楚吗？
可改进为：
- "我认为这修复了 [issue 链接]。"
- "这是在修复 [issue 链接] 里的 bug 吗？"
- "这看起来就是我们遇到的 [失败构建链接] 那个 bug。多谢修复！"

## 如何给出好的代码评审

### 提问

我把 pull request 作者视为对他们改动最有上下文的人。我可以基于自己的经验（在 Ruby on Rails 单体、TypeScript、或一个高流量数据库上的工作经验）指出我看到的问题，但我信任作者对我问题的回答。我把他对细节的理解看得比我的更好。

我还喜欢提那些触及代码所做假设的问题。他们处理的数据是什么形状？存在不符合那个形状的数据吗？代码对那应对得好吗？代码资源密集吗？性能会好吗？作为评审人，我最喜欢的回应是作者提供一个自动测试来验证那些场景的行为；第二喜欢的回应是经验数据，比如数据仓库里的一个查询、或一张显示"为什么那些场景不是问题"的 Datadog 图。

作为 pull request 作者，我也喜欢收到问题。当有人提问，就有了空间让我解释为什么对自己的改动有信心——必要时引用 issue、查询或图表。也让我能把知识和经验分享给别人。作者不仅看到我的回应，其他评审人和将来追查过去决策上下文的读者也会看到。

### 给予肯定

除了提问，对 pull request 里你认同的部分发表评论也是好习惯。这些评论可以突出"你读懂了正在改的东西"，或"你验证了代码里的某个假设"。几个例子：
- "看起来这与本模块其他类用的模式一致。"
- "谢谢你为这个加了测试！"
- "这比之前可读多了。"

根据我的经验，收到这类评论也让人舒服。接受代码评审有时会让人心累。当我在应付多方的问题和建议时，能收到几条"不向我索取任何东西、而是支持和认可我已付出工作"的评论，是很大的提振。

### 警惕偏见与假设

很容易让你的偏见——关于评审人或他们改动的代码区域——影响你的评审。你会习惯某人在某个区域工作、或有一定资历，就假设他们知道自己在做什么——但人人都会犯错。你的眼睛落在他们的改动上，你的问题核查他们的假设、或验证你自己的假设，就能在问题部署之前抓住它。

我很重视写测试，因为它们去掉一些偏见。当你写一个测试来检查代码是否正确工作时，你不必只听作者说，你只需看测试是否通过——当然，前提是测试写对了。😅

我也很看重初级开发者向资深开发者提问题（在代码评审里），即使他们认为自己的问题很蠢、或有显而易见的答案。如果对你而言不显然，那就是成立的。对别人也不显然！去问，给作者空间写下答案，把这份教育留给后来者。

### 批不批准

我把我的评审看作一道闸门，可能挡住另一个人改进我们产品，所以我审慎地保留批准。我常有自己的个人偏好、建议作者做一些可选改动，但不会仅凭那些就扣下批准。如果我对某人的 pull request 有建议、但他们的 pull request 现状不会搞坏生产、不会负面影响用户、也不会引起其他问题，我会带着那些评论批准。作者可以选择在合并前处理我的反馈，也可以在另一个分支跟进。

评审代码时记住你建议的重要性。值得为采纳你的建议而推迟上线吗？值得为它走"作者看到反馈→做建议改动→等 CI→重新评审→部署→最终合并"的整个循环吗？如果一个建议的缺席不会让某人的一天更糟，就让作者决定是否、以及何时去做这个改动。

"Request changes"（请求修改）选项会让 pull request 在评审人回来批准前无法合并。我极少用它，因为它通常感觉太重了。我信任我的团队知道何时批准 pull request，所以队友的批准可以代替我的。同样，我信任 pull request 作者会尊重并考虑我的反馈，不会因为别人批准了而我没批就盲目合并。我大概只有在"认为有紧迫的安全问题、又担心他们在合并前看不到我的顾虑"时，才会选"Request changes"。

## 如何最大化代码评审的价值

### 先评审自己的代码

GitHub 资深软件工程师 Paul Smith 教我先在请别人评审之前评审自己的 pull request，我也建议你这么做。先过一遍，对非显而易见的改动、或你在别人 pull request 里看到会问的东西，留下行内评论。自我评审也有助于判断 pull request 是否太大、拆分会不会更好。（顺带一提：如果你在乎 pull request 小而精，可以用 lerebear/sizeup-action 自动给 pull request 打上表示复杂度和规模的标签。）

### 欢迎合并后的评审

如果我碰巧在别人评审之前就合并了一个 pull request，我仍欢迎他们的评审。如果我的 pull request 弄坏了什么、或有非预期的后果，在 pull request 上评论说明，就为将来的读者留下了一条追踪线索。如果我收到对已合并 pull request 的评审，我会像它落地之前那样处理反馈。可能是评论解释我的观点，可能是额外的 pull request 迭代我最初上线的代码，也可能是开新的 issue 来承接后续工作。

### 用草稿 pull request

创建新 pull request 时，你可以选择把它设为草稿（draft）。我很依赖草稿阶段来表明是否想要评审。例如，如果必需的 CI 构建在失败、或我还没完成，我会保持草稿。我也倾向于对别人的 pull request 有同样预期：如果是草稿，我假设作者还没准备好被评审；如果标记为"可供评审"，我假设"拿到足够的批准"是阻止他们部署的唯一障碍。草稿状态意味着 pull request 还没完成，所以解决合并冲突或处理评审反馈时，我会把 pull request 移回草稿。如果我必须改代码，我会先把 pull request 标记为草稿，以免淹没已经评审过的人。移回"就绪"时会向那些评审人发送 GitHub 通知，让他们再看一次。

### 保持得体

"用蜜比用醋能捉到更多苍蝇"这句话浮现脑海。我想要我的 pull request 被评审，所以我喜欢回复自己 pull request 上的评论——尤其当我不同意评审人时。即使我不写回复，也常会用 👍 表示同意、用 ❤ 表示感谢。我希望评审人相信他们的建议不会被遗忘，所以我通过评论让他们保持在环内。如果我同意他们的建议——比如进一步重构现有代码——我可能会一边这么说、一边就"在当前 pull request 里做那个改动"提出异议。当我在后续 pull request 里处理他们的反馈时，我会回来提供链接、让评审人知道他们的反馈没有石沉大海。我也会在实现建议改动的后续 pull request 里 @他们，并注明"这回应了 @某某 在 <上一个 pull request URL> 的反馈"。这既为其他读者提供上下文，也是对原评审人的致意、给他们记一功。

当你兑现"在后续分支处理反馈"的承诺，会帮你与评审人建立信任——这能让他们更放心地批准你未来的 pull request，因为他们知道你不会留下没做完的东西。

## 小结

代码评审对产品质量的重要性怎么强调都不为过，在 AI 生成代码的时代尤其如此。在我的职业生涯里，很多次一个缺陷被抓住、一次事故被避免，就靠那一双额外的眼睛。代码评审完全值得时间投入——无论花在每日评审、理顺流程、还是搭建自动化去支持它。开发者现在彻底评审 pull request，比将来处理一个已上线到生产的、迟来的问题更快、也更不痛苦。

谢谢你这么在乎代码质量、读了我的代码评审心得。你最近查过你的评审队列了吗？也许现在是把这些想法付诸行动的好时机。想了解更多如何在 GitHub 上使用 pull request 评审，可查看 GitHub 社区上 Staff DevOps Architect Mickey Gousset 和 Joshua Johanning 合写的《评审 pull request 的 5 个技巧》。
