# 编码智能体 101：真正把事做完的艺术（Coding Agents 101）

> 来源：Cognition 团队（2025 年 6 月，约 15 分钟阅读），课程 Week 3 阅读

现在是 2025 年。编码智能体不是魔法，但它们是我们拥有过的最接近魔法的东西。我们注意到，有些工程师——尤其是 senior 到 staff 级别——比其他人更快取得成功。这里我们分享一些从客户和自身经验中提炼出来的顶级经验。

关于本指南：
- **与产品无关（Product-agnostic）**：我们讨论的技巧，可帮你用好任何编码智能体。
- **务实（Tactical）**：我们提供最中意的可执行建议。
- **技术性（Technical）**：虽然编码智能体对很多人都有价值，但本指南面向工程师。

开发者工具在快速演进。十年前，是自动补全和 intellisense，能建议方法名、执行程序化重构；四年前，是 copilot 和 tab 补全，能帮你写下接下来几行代码；两年前，是生成式聊天机器人，能辅助你的开发、为你生成整个文件；今天，是**自主智能体（autonomous agents）**，能从初始描述到最终 pull request，只需很少人工干预。过去两年我们一直通过构建 Devin 来实现这一愿景。如今，对自主智能体的兴趣达到新高，尤其是近期同类产品接连发布。这些智能体可以呈现多种形态，包括 Web 应用、移动应用，以及集成进 Slack、GitHub、Linear、Jira 等流行工具。

虽然"人 + AI 助手"能比任何单独的 AI 达成更多，但**自主智能体端到端处理任务的能力开启了新的多任务级别，把每个工程师都变成了工程经理**。

适应与这些新 AI 同事高效共事需要一些时间。有意思的是，我们观察到 senior 到 staff 级别的工程师往往最快上手并熟练这些工具。最终，这些工具会普及到工程的各个层级。基于我们的经验和客户反馈，我们想分享一些关键洞察和教训，帮助每个人把工具顺利整合进工作流。

## 提示基础（Prompting Basics）

这些基本准则能帮你在 2025 年与编码智能体有效互动。即使别的都记不住，至少记住这些。

### 说明"怎么做"，而不只是"做什么"

把智能体想象成一个决策能力不太可靠的初级编码搭档。简单任务可以直接描述；但对更复杂的任务，从一开始就要清楚勾勒你偏好的方法。提前把整体架构和逻辑交给智能体，不仅提升它的成功几率，也减少你评审代码的时间——因为你已经熟悉了预期的实现方式。

**示例**：与其说"加单元测试"，不如指明要测试哪些功能、识别重要的边界情况，并说清什么需要 mock（如果需要的话）。

### 告诉智能体从哪开始

想想如果是你自己处理这个任务，你会从哪里开始。即使你不知道具体的文件或函数名，也要提到仓库、相关文档和涉及的关键组件。清晰指出这些元素能最大限度减少浪费的精力和困惑。

**示例**："请给我们的代码加上对 Google 模型的支持。你应该看看[这里]的最新文档，并在 model groups 目录下新建一个实现文件。"

### 练习防御性提示（defensive prompting）

想象把同样的提示词给一个新来的实习生。哪里容易产生困惑或错误？预判这些点，主动澄清你的指令，避免歧义。

**示例**："请修复我们搜索模块的 C++ 绑定，让它通过新的单元测试。注意：每次改代码后，在测试前你很可能需要重新编译绑定。"

### 提供对 CI、测试、类型检查和 lint 的访问

智能体的大部分魔力，来自它们修复自身错误、对着错误信息迭代的能力。通过类型检查器、lint 和单元测试等工具提供强反馈回路，能大幅提升它们的表现。考虑用带类型的 Python 代替纯 Python、用 TypeScript 代替 JavaScript。教你的智能体如何运行常用检查和测试，确保它有全部所需包和访问权限。如果智能体能操作浏览器，给出运行前端开发环境的清晰指令。

**示例**：我们团队从大多是未带类型的 Python SDK 转向全带类型的 SDK（对编码智能体来说，这也是一个理想的练习任务）。

### 善用你的专业经验

当你熟悉自己的代码库时，上面所有方法都更容易。即使是简单任务，也能从你验证逻辑和结果的能力中受益。**人工监督仍然必不可少**——最终，你要对代码的正确性负责。即便这些工具变得越来越强大，所有权与验证仍将是人类工程师的关键职责。

## 在工作流中使用智能体

一旦掌握了与智能体对话的基本功，就该把这些 AI 帮手引入你的日常工作流。以下是一些让智能体融入日常的实用方式：

### 立刻接手新任务

想象一位队友发消息说"嘿，我们能快速做一下 X 吗？"或"我们需要调整一下 Y。"与其让它打断你的节奏，不如直接给自主智能体发个简短提示，让它调查或做出改动。这让你能专注于主线任务。有有趣的副业想法？需要快速原型、爬取数据或复现研究？委托给智能体，稍后再回来。

**示例**：许多团队在 Slack 讨论 bug 修复或小功能更新时，直接 @Devin 一下。

### 随时随地编码

设想你在通勤或旅行时突然冒出紧急 bug，或意识到代码里可能留了个错误。别担心！自主智能体往往支持移动端访问，让你即时处理。无论是通过 Slack 移动应用还是专用移动应用，许多智能体都让你在路上解决问题，即使 WiFi 信号不稳。

**示例**：这种可选项让我们自己的团队在开车和航班上生产力大增。

### 把杂活甩出去

卡在旧的 commit 二分排查，或要给新功能更新文档？把这些重复任务甩给智能体。你省下宝贵时间，专注于更有创造力和影响力的事。

**示例**：在我们团队，工程师发布改动后由智能体更新所有相关文档和面向用户的内容，很常见。

### 跳过分析瘫痪

拿不定"这次重构是否真会简化代码"？在两个架构方案间纠结？让你的智能体把两个方案都实现出来。有了可对比的具体例子，决策就直截了当了，丢弃一个方案也不会伤感情。

**示例**：在为文本框选 Lexical 还是 Slate 时，我们让智能体各实现一份。Slate 因产出更好的最终结果而胜出。

### 搭建预览部署

把 CI/CD 管线配置成：每个新 PR 自动创建预览部署，给你一个即时的在线 URL。评审 AI 智能体完成的前端任务时，这特别方便。

**示例**：Vercel 是一个让预览部署极其简单的部署平台。

## 委派更大的工单

当 pull request 的规模和复杂度超过"几个文件"后，一口气处理就变得有挑战。然而，掌握如何委派中到大型任务（通常是 1–6 小时的工作量），正是自主智能体回报率最高的地方——你省下的不再是几分钟，而是数小时的生产力。小任务或许能轻松完成，但把智能体的能力拉满去处理更大任务，才能带来最大回报。

### 自动化你的初稿

对重大任务，用自主智能体创建 PR 的初稿能推动进度、大幅削减工作量。成功的关键在于提前清晰传达你期望的方法。把自己想象成指导初级开发者的架构师。清晰、详细的指令，能避免把时间浪费在纠正智能体代码里根本性的误解上。

| 领域 | 起草（Drafting） | 打磨（Refining） |
|---|---|---|
| 新闻业 | 记者收集初始信息，写出文章初稿 | 编辑评审初稿、核实事实、润色、定稿发布 |
| 餐厅 | 切菜工备料、做初步菜品 | 副主厨加调料、把菜调得更美味，再送上食客餐桌 |
| 编码 | 自主智能体基于初始计划开工，创建初稿解决方案 | 人类开发者评审 PR 初稿、给反馈、在合并前手工精修 |

> 🛑 记住：大型任务（还）不是完全免手的。较有挑战的任务要预期多轮反馈循环，也要预期一些手工打磨。一个现实目标是省下约 **80%** 的时间，而非完全自动化——你的专业经验对验证和最终质量保证仍然至关重要。

### 共同开发 PRD

对复杂或定义模糊的任务，与你的自主智能体协作制定详细计划可能非常高效。你起初不知道每个细节或需求完全没问题。先从让智能体探索一些发现性问题开始，比如"我们的认证系统如何运作？"或"哪些服务可能受影响？"你还可以让智能体先标出具体相关代码目标，供你尽早确认。

某些智能体（如 Devin 和 Claude Code）提供专门的规划模式，专注于阅读和探索现有代码，而非立即修改。如果你希望在委派前做更充分的准备，deepwiki.com 和 Devin Search 等专门的代码库搜索工具能快速提供你代码库的洞察，帮助简化流程。

### 设置检查点

对多部分任务——尤其是涉及多个代码库的——沿途设立清晰的检查点：

`计划 → 实现一块 → 测试 → 修复 → 检查点评审 → 下一块`

在每个重要阶段后明确要求暂停，尤其是横跨多层（数据库、后端、前端）的复杂功能。用这些检查点确保实现符合你的预期、澄清疑问（如"解释认证流程并确认它安全"）、并尽早纠偏，避免级联问题。

**示例**："我想让你实现这个横跨我们数据库、后端和多个前端界面的功能。请先规划所需的数据库 schema 变更，完成后告诉我，我好应用迁移。" → "现在请实现后端改动，并加测试确保 XYZ 可用。完成后告诉我。" → "现在请在我们 web 和移动两个界面都实现改动，以调用新的后端端点。"

### 教它验证自己的工作

给反馈时，不要只指出问题（"这个函数不工作"）。清晰表述你的测试流程，让智能体能独立验证未来的任务。对你会反复使用的测试模式，把它们纳入智能体持久的知识库（见"加入智能体的知识库"）。

**示例**：在 Devin 里，我们积极提示用户把关键的测试流程存进智能体的长期记忆，简化后续交互。

### 提高 AI 高发区的测试覆盖

目前智能体还不能面面俱到地交互式测试所有场景。在 AI 改动频繁的区域加强测试覆盖，能对智能体的输出更有信心。扎实的测试意味着：看起来正确的代码可以放心合并。

**示例**：在把实现从 Python 交给 AI 翻译成 C 之前，我们先加强了代码库关键部分的单元测试。

## 自动化工作流

智能体响应事件的反应速度比人快得多，而且比人更愿意干无聊、重复的活。

### 为最重复的工作创建快捷方式

工程团队经常遇到重复、例行的任务，这些是智能体自动化的绝佳候选。常见例子：feature flag 移除、依赖升级、为新功能 PR 修复并补测试。要高效搭建，通常由有经验的工程师创建一个健壮、可复用的提示词模板——在 Devin 里，它们叫 playbook，可针对这些场景反复运行。

**示例**：我们一个客户配置了每当开发新功能就自动触发三个专职写单元测试的智能体。

### 智能代码评审与执行

虽然存在专门的快速代码评审工具（如 Greptile 和 CodeRabbit），自主智能体也能是提供更准确洞察的有趣选项——尤其是当它们已经索引了你仓库的功能时。

**示例**：在 Cognition，我们喜欢维护一份"工程师最常犯错误"的清单并提交进代码库。然后，与其写经典的 lint 规则去捕获它们（这往往不可行），我们让一个智能体在每个新 PR 上运行、检查这些错误。

### 接入事件与告警

你还可以让自主智能体响应特定事件自动触发。例如 Devin 提供可访问的 API，其他智能体可以通过 CLI 命令集成进自定义工作流。这些配置与 MCP 配合尤其好，能摄入第三方错误日志。

> ⚠️ 在生产服务上做问题分诊时，AI 的调试能力其实没那么强。与其让 AI 端到端地即时修复 bug，更实际的做法往往是让 AI 只标记出最可疑的错误、变更等。

## 定制与性能提升

### 环境设置

没有什么比"不完整或不匹配的环境"更能拖慢智能体。要让一切顺畅，把你的智能体环境与团队环境精确对齐：包括语言版本、包依赖和自动化检查。例如，pre-commit 应安装在智能体环境里；环境配置（密钥、语言版本、虚拟环境、浏览器登录态）应使用 `.envrc` 或自定义 `.bashrc` 配置自动获取。

**示例**：我们把智能体的浏览器设置为预先认证的登录态，省去了手动认证的麻烦，也让测试更容易。

### 构建自定义 CLI 工具和 MCP

MCP 广泛可用，搭建快捷，适合实验如何把智能体连接到外部工具。但很多人忽略了为智能体搭建简单的 CLI 脚本。举个简单例子：你可以给智能体一个"根据工单 ID 拉取 linear 工单信息"的脚本；你也可能想给它一个可靠完成工作流常见环节的工具，比如重启本地开发环境的脚本。

**示例**：我们有个客户创建了一个只展示测试套件中第一个失败测试的 CLI 工具，取得了很大成功。这个 CLI 引导智能体只聚焦那个测试并附详细错误信息，让智能体在长任务上有更高的成功率和更快的完成速度。

### 加入智能体的知识库

如果你的智能体犯了某些常见错误，正是把反馈编码进智能体知识库的好时机。在 Devin 里有一套专门的知识管理系统。许多产品提供 `.rules` 文件、`.md` 文件供智能体持久摄入。不要只给它所用框架的准则，还要告诉它你项目的整体架构、不同类型任务常用什么测试、如何运行重要命令、你推荐用哪些工具。

**示例**：我们给智能体传授了"添加新服务路由时应遵循的具体流程"的知识，包括它需要在前端和后端添加样板代码的所有地方。结果，这些任务如今都能轻松委派给我们的 AI。

## 自主智能体的局限

### 有限的调试能力

Bug 报告可能看起来很简单，但许多 bug 不仅需要访问数据库和日志，还需要比当今大多数 AI 智能体更高的调试水平。如果要用 AI 辅助调试，我们建议让它列出一份"可能的根本原因清单"，而不是让它自己排查并修复一切。然后由人根据自己的经验判断哪个才是真正的根因。不过，一旦根因已知，智能体在实现修复上仍相当得力。

### 欠佳的细粒度视觉推理

总的来说，当今模型在"匹配设计截图或 Figma mockup 所需细节级别"的视觉推理上能力不强。它们在最可靠的是能用代码级别描述的画面（例如给它 Figma 的代码）。如果你想让它们匹配你的视觉风格，应该用带可复用组件的好设计系统。

### 知识截止

每当你要用一个新库时，应明确把它指向最新文档。否则，由于预训练基础模型的知识截止，大多数智能体会沿用这些库的旧模式。一个好智能体在你指向文档后能克服这一点，但你必须保持警惕（记住，智能体甚至不知道这些库有新版本）。

## 管理时间、最小化损失

并非每次用智能体都会成功。在 2025 年，这些智能体的结果存在真实方差。工作的一部分，就是学会以"最大化成功概率、最小化浪费的时间和 token"的方式使用它们。

### 更早地愿意止损

新手用智能体常犯的错误：即使智能体的工作已偏离轨道，仍执着于让这次交互成功。如果你发现自己想着"它在无视我的指令"或"这东西在兜圈子"，你就该放心地终止那次对话或手动接管。继续发更多消息，更可能是"你的任务内在复杂度超出了智能体能力"的信号，而非一个可以纠正的小错误。

### 分散你的实验

如果你是智能体新手，建议一开始分散下注。尝试一系列不同的提示词和想法。在智能体天然擅长的任务类型上加注，在它不擅长的上及时止损。不必每次都想逼智能体成功。

### 进展停滞时重新开始

对智能体，"从头再来"正确的次数远多于对人。如果你给智能体一个任务而它难以响应反馈或纠正方向，用一个全新智能体、把所有指令前置地给全，往往能更快抵达成功。智能体修复一团糟的环境的能力，远不如它从零吐出全新代码的能力。

## 安全与权限

### 为智能体创建账号

一个一次性邮箱对安全测试网站很有用。如果智能体需要访问云资源，为它创建定制的 IAM 角色。

### 给它开发/预发环境

理想情况下，智能体使用与团队工程师相同的测试环境。我们建议完全避免给它生产服务的访问权。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

尽量给它只读访问权。我们发现，任何与外部服务交互的脚本，仍由人手动运行会更好。

## 巨变在前

我们坚信软件工程师不会消失。即便编码智能体越来越聪明、越来越能干，深层技术专长和对代码库的熟稔依旧弥足珍贵。对项目、系统和代码的真正所有权，现在比任何时候都更关键。在我们今天的团队里，工程师被期望在保持深刻理解与审慎判断的同时，监管多个系统。当自动化放大你的影响力时，"同时处理并行任务"的能力将不只是可能，而是**必备**。我们乐于分享在为自身组织迎接这场转变过程中积累的洞察，让你和你的团队也能在日新月异的软件开发世界中茁壮成长。
