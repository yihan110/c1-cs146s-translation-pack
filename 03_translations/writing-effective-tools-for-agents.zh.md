# 用智能体编写更高效的工具（Writing Effective Tools for Agents）

> 来源：Anthropic Engineering（Sep 11, 2025），课程 Week 3 阅读

> 智能体的效能，取决于我们给它的工具。本文分享如何编写高质量的工具和评估（evaluations），以及如何通过让 Claude 为自身优化工具来提升性能。

模型上下文协议（MCP）可以让大语言模型（LLM）智能体拥有成百上千个工具来解决现实任务。但我们如何让这些工具发挥最大效能？

在本文中，我们介绍在各种智能体驱动型 AI 系统中提升性能的最有效技术。

我们首先说明如何：
- 构建并测试你的工具原型；
- 创建并运行针对工具的全面的智能体评估；
- 与 Claude Code 之类的智能体协作，自动提升工具的性能。

最后，我们总结在过程中识别出的编写高质量工具的关键原则：
- 选择该实现（和不该实现）的工具；
- 用命名空间（namespacing）划清功能边界；
- 从工具返回有意义的上下文给智能体；
- 为 token 效率优化工具响应；
- 对工具描述和规格做提示工程。

## 什么是工具？

在计算中，**确定性系统**面对相同输入每次都产生相同输出；而**非确定性系统**——例如智能体——即使起始条件相同也可能产生多变回应。

传统上我们写软件，是在确定性系统之间建立契约。例如，`getWeather("NYC")` 这样的函数调用，每次都会以完全相同的方式获取纽约的天气。

**工具是一种新类型的软件，反映的是确定性系统与非确定性智能体之间的契约。** 当用户问"我今天要不要带伞"时，智能体可能调用天气工具，可能凭常识回答，甚至可能先澄清地理位置。偶尔，智能体还会产生幻觉，或未能理解如何使用某个工具。

这意味着我们要从根本上重新思考"为智能体写软件"的方式：**不能像给其他开发者或系统写函数和 API 那样去写工具和 MCP 服务器，而要专门为智能体设计它们。**

我们的目标是扩大"智能体通过使用工具、采取多种成功策略来高效解决广泛任务"的表面积。幸运的是，根据我们的经验，对智能体最"符合人体工学（ergonomic）"的工具，对人来说最终也往往出奇地直观。

## 如何编写工具

本节说明如何与智能体协作，编写并改进你给它们的工具。先从快速搭起工具原型并在本地测试开始；接着运行全面评估来衡量后续改动；与智能体并肩工作，你可以不断重复"评估→改进"循环，直到你的智能体在现实任务上取得强劲表现。

### 构建原型

在亲自上手之前，很难预见哪些工具对智能体来说符合人体工学、哪些不是。先从快速搭建工具原型开始。如果你用 Claude Code 编写工具（甚至可能一次性生成），最好把工具将依赖的任何软件库、API 或 SDK（包括可能的 MCP SDK）的文档提供给 Claude。对 LLM 友好的文档通常能在官方文档站的平铺 `llms.txt` 文件中找到（这里是我们 API 的示例）。

把工具包进本地 MCP 服务器或桌面扩展（DXT），就能在 Claude Code 或 Claude Desktop 应用中连接并测试它们。连接本地 MCP 服务器到 Claude Code，运行 `claude mcp add <name> <command> [args...]`；连接到 Claude Desktop 应用，分别在 Settings > Developer 或 Settings > Extensions 中操作。工具也可以直接传入 Anthropic API 调用做程序化测试。

自己先测一遍工具，找出所有粗糙边缘；收集用户反馈，建立对工具预期要支撑的用例与提示词的感觉。

### 运行评估

接下来，你需要通过运行评估来衡量 Claude 使用工具的效果。先从基于真实世界用例生成大量评估任务开始。我们建议与智能体协作，帮你分析结果、确定如何改进工具。完整的端到端流程可参考我们的《工具评估 cookbook》。

#### 生成评估任务

有了早期原型，Claude Code 能快速探索你的工具，生成几十组"提示词-响应"对。提示词应受真实用例启发，基于真实的数据源和服务（例如内部知识库和微服务）。建议避开过于简单或表面的"沙箱"环境——它们无法用足够的复杂度来压力测试你的工具。强有力的评估任务可能需要多次工具调用——甚至多达几十次。

强任务示例：
- "下周与 Jane 安排一次会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的笔记，并预定一间会议室。"
- "客户 ID 9182 反馈在一次购买尝试中被扣款三次。找到所有相关日志条目，判断是否有其他客户受同一问题影响。"
- "客户 Sarah Chen 刚提交了取消请求。准备一份挽留方案。确定：(1) 她离开的原因，(2) 最有说服力的挽留方案，(3) 出价前我们应关注的任何风险因素。"

弱任务示例：
- "下周与 jane@acme.corp 安排会议。"
- "在支付日志中搜索 purchase_complete 和 customer_id=9182。"
- "找到客户 ID 45892 的取消请求。"

每个评估提示词都应配一个**可验证**的响应或结果。你的验证器可以简单到"把真实答案与采样响应做精确字符串比较"，也可以高级到"让 Claude 评判响应"。要避免过严的验证器——它们会因格式、标点或合法的替代措辞等无关差异而误拒正确响应。

对每个"提示-响应"对，你还可以（可选）指定你期望智能体在解题时调用的工具，以衡量智能体是否成功领会每个工具的用途。但由于正确解题可能有多种路径，尽量别过度指定或过拟合到特定策略。

#### 运行评估

我们建议用直接的大语言模型 API 调用程序化运行评估。用简单的智能体循环（while 循环包裹交替的 LLM API 调用和工具调用）：每个评估任务一个循环。每个评估智能体应只给一个任务提示词和你的工具。

在评估智能体的系统提示词里，建议指令智能体不仅输出结构化的响应块（供验证），也输出推理块和反馈块。在工具调用和响应块之前要求它们输出这些，可能通过触发思维链（CoT）行为来提升 LLM 的有效智能。

如果你用 Claude 运行评估，可以开启交错思考（interleaved thinking）来获得类似的开箱即用功能。这有助于探查智能体为何调用/不调用某些工具，并凸显工具描述与规格中可改进的具体地方。

除了整体准确率，我们还建议收集其他指标：单个工具调用与任务的总体运行时长、工具调用总数、总 token 消耗、工具错误。跟踪工具调用有助于揭示智能体常见的运行工作流，并为工具合并提供机会。

#### 分析结果

智能体是你发现问题的得力伙伴，能就"相互矛盾的工具描述、低效的工具实现、令人困惑的工具模式"等给出反馈。但要记住：**智能体在反馈与回应中省略的东西，往往比它们包含的东西更重要**——LLM 并不总是言为心声。

观察你的智能体在哪里卡壳或困惑。通读评估智能体的推理与反馈（或思维链），找出粗糙边缘。审阅原始转录（包括工具调用与工具响应），捕捉任何未在智能体思维链中明确描述的行为。要读出弦外之音；记住，你的评估智能体未必知道正确答案和策略。

分析你的工具调用指标。大量冗余的工具调用，可能意味着需要调整分页或 token 上限参数；因无效参数而产生的大量工具错误，可能意味着工具需要更清晰的描述或更好的示例。当年我们发布 Claude 的 web 搜索工具时，发现 Claude 在工具查询参数上无谓地追加 "2025"，导致搜索结果偏差、性能下降——我们通过改进工具描述把 Claude 引向了正确方向。

### 与智能体协作

你甚至可以让智能体替你分析结果、改进工具。只需把评估智能体的转录拼接起来粘贴给 Claude Code。Claude 擅长分析转录并一次性重构大量工具——例如，确保新改动后工具实现与描述仍自洽。

事实上，本文的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评估建立在内部工作区之上，镜像了内部工作流的复杂度，包括真实项目、文档和消息。

我们依赖留出验证集（held-out test set）确保不过拟合到"训练"评估。这些验证集揭示，我们还能提取到比"专家"工具实现（无论由研究人员手写还是由 Claude 生成）更多的性能提升。

## 编写有效工具的原则

本节把我们学到的浓缩为几条指导原则。

### 为智能体选对工具

**工具越多并不总是结果越好。** 我们观察到一个常见错误：工具只是简单包装现有软件功能或 API 端点——无论这些工具是否适合智能体。这是因为智能体相对于传统软件有独特的"可供性（affordances）"——它们感知"用这些工具能采取什么潜在行动"的方式不同。

LLM 智能体的"上下文"有限（即单次能处理的信息量有上限），而计算机内存便宜且充裕。以在通讯录中查找联系人为例：传统软件程序可以高效地逐条存储和处理联系人，逐个核对再继续。但如果 LLM 智能体使用一个"返回全部联系人"的工具、再逐 token 读一遍，它就把有限的上下文空间浪费在无关信息上了（想象在通讯录里从第一页逐页读到最后一页来查找——即暴力搜索）。对智能体和人都更好、更自然的做法是：先跳到相关的页面（也许按字母顺序找到它）。

我们建议构建**少量深思熟虑的、针对高影响工作流的工具**，与你的评估任务匹配，再从这里扩展。在通讯录这个例子里，你或许会选择实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts` 工具。

工具可以合并功能，在内部处理可能多个的离散操作（或 API 调用）。例如，工具可以把相关元数据补充进工具响应，或把经常串联的多步任务合并进一次工具调用。示例如下：
- 与其实现 `list_users`、`list_events` 和 `create_event`，不如实现一个 `schedule_event` 工具——它同时查找空闲并安排事件。
- 与其实现 `read_logs`，不如实现 `search_logs`——只返回相关日志行和少量上下文。
- 与其实现 `get_customer_by_id`、`list_transactions` 和 `list_notes`，不如实现 `get_customer_context`——一次性汇总客户近期所有相关信息。

确保你构建的每个工具都有清晰、独特的用途。工具应让智能体像人一样（在拥有相同底层资源的前提下）细分并求解任务，同时减少本会被中间输出消耗的上下文。

**工具太多或相互重叠，也会让智能体偏离高效策略。** 谨慎、有选择地规划你要构建（或不构建）的工具，回报可观。

### 给工具加命名空间

你的 AI 智能体可能获得几十个 MCP 服务器和数百个不同工具的访问权——其中还包括其他开发者写的。当工具功能重叠或用途含糊时，智能体会困惑该用哪个。

**命名空间**（把相关工具归到共同前缀下）有助于划清大量工具之间的边界；MCP 客户端有时默认这么做。例如，按服务命名空间（`asana_search`、`jira_search`）和按资源命名空间（`asana_projects_search`、`asana_users_search`），能帮助智能体在正确时机选对工具。

我们发现，选择基于前缀还是基于后缀的命名空间，对我们的工具使用评估有不可忽视的影响。影响因 LLM 而异，我们鼓励你根据自己的评估选择命名方案。

智能体可能调用错工具、用错参数调用对工具、调用过少工具、或错误处理工具响应。通过有选择地实现"名称反映任务自然细分"的工具，你同时减少了加载进智能体上下文里的工具和工具描述数量，并把智能体的计算从上下文转移回工具调用本身——从而降低智能体整体犯错的风险。

### 从工具返回有意义的上下文

同理，工具实现应只向智能体返回高信号信息。它们应优先保证**上下文相关性**而非灵活性，并回避底层技术标识符（例如 uuid、256px_image_url、mime_type）。`name`、`image_url`、`file_type` 这类字段更可能直接指导智能体的后续行动和回应。

智能体处理自然语言名称、术语或标识符的能力，往往远强于处理晦涩标识符。我们发现，仅把随机的字母数字 UUID 解析成更有语义、更可解释的语言（甚至一个从 0 开始的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

某些情况下，智能体可能需要同时与自然语言和技术的标识符输出交互——哪怕只是为了触发下游工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以通过在工具中暴露一个简单的 `response_format` 枚举参数来同时支持两者，让智能体控制工具返回"简洁"还是"详细"的响应（见下图）。你还可以添加更多格式以获得更大灵活性，类似 GraphQL 那样精确选择要接收的信息。下面是一个控制工具响应详略度的 `ResponseFormat` 枚举示例：

```
enum ResponseFormat {
  DETAILED = "detailed",
  CONCISE = "concise"
}
```

（详细工具响应示例：206 tokens；简洁工具响应示例：72 tokens。）Slack 线程和线程回复由唯一的 `thread_ts` 标识，获取线程回复必需它。`thread_ts` 和其他 ID（`channel_id`、`user_id`）可以从"详细"工具响应中取回，以支持需要它们的后续工具调用；"简洁"工具响应只返回线程内容并排除 ID。在这个例子里，我们用"简洁"工具响应只花了约三分之一的 token。

甚至你的工具响应结构——例如 XML、JSON 或 Markdown——也会影响评估性能：没有放之四海皆准的答案。这是因为 LLM 基于 next-token 预测训练，往往对与其训练数据匹配的格式表现更好。最优响应结构因任务和智能体而异。我们鼓励你根据自己的评估选择最佳响应结构。

### 为 token 效率优化工具响应

优化上下文的质量很重要，优化返回给智能体的上下文的**数量**同样重要。

我们建议：对任何可能消耗大量上下文的工具响应，实现分页、范围选择、过滤和/或截断的某种组合，并带合理的默认参数值。对 Claude Code，我们默认把工具响应限制在 25,000 token。我们预计智能体的有效上下文长度会随时间增长，但对"上下文高效工具"的需求会一直存在。

如果你选择截断响应，务必用有用的指令引导智能体。你可以直接鼓励智能体采取更省 token 的策略，例如对知识检索任务做"多次小而精准的搜索"而非"一次大而全的搜索"。同样，如果工具调用报错（例如输入校验失败），你可以对错误响应做提示工程，清晰传达具体、可执行的改进建议，而不是晦涩的错误码或堆栈。工具截断和错误响应可以引导智能体走向更省 token 的工具使用行为（用过滤或分页），或给出格式正确的工具输入示例。

### 对工具描述做提示工程

现在我们讲到改进工具最有效的方法之一：**对工具描述和规格做提示工程**。由于它们会加载进智能体的上下文，能共同引导智能体形成有效的工具调用行为。

写工具描述和规格时，想想你会如何向团队里的新人描述这个工具。考虑你可能隐式带入的上下文——专门的查询格式、小众术语的定义、底层资源之间的关系——并把它显式化。清晰描述（并用严格数据模型强制）期望的输入和输出，避免歧义。尤其，输入参数要命名得毫不含糊：与其叫 `user`，不如叫 `user_id`。

有了评估，你可以更有信心地衡量提示工程的影响。对工具描述哪怕是微小的精修，也可能带来巨大的改进。Claude Sonnet 3.5 在 SWE-bench Verified 评估上取得当前最佳性能，正是因为我们对工具描述做了精准精修，大幅降低了错误率并提升了任务完成度。

工具定义的其他最佳实践可参考我们的《开发者指南》。如果你在为 Claude 构建工具，还建议了解工具如何被动态加载进 Claude 的系统提示词。最后，如果你在写 MCP 服务器的工具，工具注释（tool annotations）有助于披露哪些工具需要开放世界访问、或会做出破坏性修改。

## 展望未来

要为智能体构建有效工具，我们需要把软件开发实践从"可预测、确定性的模式"转向"非确定性模式"。

通过本文描述的迭代式、评估驱动流程，我们识别出使工具成功的稳定模式：**有效的工具是刻意且清晰定义的、审慎使用智能体上下文的、能在多样化工作流中组合的、能让智能体直观解决现实任务的。**

未来，我们预期智能体与世界互动的具体机制会不断演进——从 MCP 协议的更新到底层 LLM 本身的升级。用系统化、评估驱动的方法改进智能体的工具，我们就能确保：随着智能体越发强大，它们使用的工具也随之进化。
