# 软件团队的代码评审要点（Code Review Essentials for Software Teams）

> 来源：Blake Smith 博客（2015-02-09），课程 Week 7 阅读

代码评审是任何协作软件项目不可或缺的一部分。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一个稳健的流程，让它的成员——以及代码库本身——朝着正确的方向前进。

代码评审是一个强大的工具，它：
- 帮助团队成员在系统变化时更新他们对系统的心智模型（mental model）；
- 确保改动正确解决问题；
- 开启关于设计优劣的讨论；
- 在缺陷进入生产前抓住它们；
- 保持代码风格与组织的一致性。

把这些好处想成一个需求层级，会有帮助。

## 让团队成员保持一致

代码评审最关键的功能，是让团队的每个成员都朝正确方向前进。你无法安全地改动一个你不理解的系统，所以代码评审让团队在思想上保持对齐。当 Bob 为会计子系统提交一个 pull request，Amy 在评审 Bob 代码时让心智模型保持更新。Amy 有机会就她不理解的部分提问，Bob 则受益于澄清他的设计决策、并向别人讲解他的工作。一个月后 Amy 要改会计子系统时，她的心智模型已经是最新的、随时可用。她花更少时间读代码、在脑子里拼系统，更多时间思考更高层的抽象和设计。每个人都赢，因为每个人都保持一致。

## 执行一个好的 pull request

在你写一行改系统的代码之前，先问自己这些问题：
- **"这是正确该做的事吗？"** 客户、内部团队成员和其他方总有竞争性的需求。这是在你深入之前厘清优先级的有效方式。迭代/冲刺规划会议等其他流程也有助于保持正轨。
- **"团队已经认同这个改动是正确的吗？"** 如果没有，最好先通过邮件或当面开启设计讨论。当人们在改动之前就对设计达成一致，你的改动更可能被接受。
- **"我如何把这个改动拆成容易评审和理解的小块？"** 小的改动更容易思考和理解。好的讨论源于团队能快速理解你的改动。如果你的改动巨大，队友会眼神呆滞，你可能只得到几条风格上的吹毛求疵。
- **"我打算如何测试这个改动以消灭 bug 并确保正确性？"** 你可能有一个 QA 部门，但作为开发者，交付高质量可用软件仍是你的职责。容易测试的软件通常更解耦、被拆成更小块、更容易推理。你所有改动都需要一个测试计划。

我发现提前回答这些问题，从长远看省了我很多头疼。你最不想要的，是花好几天写改动、结果却因根本性设计缺陷或团队分歧而被拒绝；或者改动因无人能验证其正确性而被卡住。再说一遍，目标是"在改动系统的同时让其他成员跟上你的改动"。问自己"如何把工作拆成一口一口的小块、并测试这些块"，在很多方面都有帮助：它降低风险；让改动更容易推理；推动你走向更好的设计。你宁愿用手术刀做许多小而精准的切口，也不愿用砍刀砍一道巨大的伤口。在多数增量的情况下我偏好"手术刀式"开发，把"砍刀"留给删除大块死代码的时候。

## 发送 pull request

好，你已经得到团队对你改动的认可，也实现了你计划的设计。那么最有效的发送 pull request 的方式是什么？你一直在努力做改动，想让团队其他人注意你的 pull request 并快速反馈。怎么做？

还记得我前面说"代码评审最重要的部分是让团队共同的、集体心智模型保持对齐"吗？你的队友可能在做和你完全不同的事——也许在系统的完全不同部分。他们的大脑处在完全不同的上下文里，所以你必须通过给他们评审所需的有益指引来克服这点。这意味着写一个组织良好的描述，说明你做了什么改动、为什么做、以及他们仅靠读代码得不到的任何相关信息。别让你的队友做超出必要的脑力劳动。

看几个好坏的 pull request 描述示例。

**坏示例：**
```
标题：修复未初始化内存 bug
描述：
这是 Bob 和我之前讨论过的那个 bug。我在编译器上遇到麻烦，
但总算让它工作了。大家看看觉得怎么样。
```
如果你是这位开发者，停下来、把自己放进评审人的鞋里一秒钟。标题含糊，提出的问题比回答的还多：内存 bug 在哪？这个改动有多关键？Bob 和你之前讨论的 bug 是什么？你在编译器上遇到什么麻烦？描述没提供任何关于问题的有益上下文，也没提供你改动的有益描述。如果这个 pull request 很长，评审人将不得不深入代码、做脑力体操试图获取上下文，然后才有机会思考这个改动如何融入系统的连贯设计。

**改进示例：**
```
标题：修复进程启动时因未初始化内存崩溃 [#54633]
描述：
这个 bug 因我们统计 Counter 类里的内存初始化错误，导致进程启动时崩溃。
我和 Bob 讨论过，我们都认为崩溃是罕见的边界情况，不值得发 hot-fix 版本。
以下是改动摘要：
- 把底层的 int 变量移入类初始化器，防止 Counter 里出现未初始化内存。
- 重做了 Counter 接口，简化调用方条件逻辑，防止进一步的 off-by-one 计数问题。
- 加了一个能暴露崩溃的单元测试。

测试：我已验证测试套件仍然通过，并手动验证本地不再崩溃。
```

这个 pull request 描述改进的几点：标题有足够的描述性，给评审人一些简短上下文、吸引他们点开邮件了解更多。评审人知道那是进程崩溃（通常是件坏事），而且有一个 bug 报告编号，如果他们想多了解问题，可以查看更多细节。新描述还勾勒了问题发生在哪里、帮助了解修复有多关键。有一个列出 pull request 高层结构改动的摘要，会在评审人看代码之前就给他们一幅改动的心智图——评审人不应为看到的东西感到意外。这个示例还勾勒了执行的测试，给评审人信心：改动经过深思熟虑、经过测试、可以合并。**让评审人点击"merge"变得极其容易，就是为他们的成功铺路。**

## 评审人：给出建设性反馈

评审流程的下一部分，是考虑如何给同行建设性反馈。如果目标是清晰和对齐，给出高质量的、建设性的反馈能帮每个人都更理解系统、推向更好的代码。

避免说这样的话：
- **"这个设计坏了。"** 为什么坏了？怎么改更好？这样的话打击信心、挫伤自尊。
- **"我不喜欢这个改动。"** 你为什么不喜欢？你想要什么替代？不喜欢某样东西可以，但你应该明确表达想法、提供关于如何改进代码的有用线索。
- **"你能重写得更清楚吗？"** 我现在这样有什么问题？我该怎么重写？什么不清楚？这类评论本身就不清楚，也没给出一条简单的前进路径。

改为说这样的话：
- **"这段代码如何处理负整数？"** 这条反馈很具体，促使开发者自己思考后果。作为评审人，你可能知道这段代码遇到负整数会崩，但让开发者自己领悟更好。这类问题也可能表明测试缺口、或需要进一步明确范围。
- **"这部分让我困惑，我不明白为什么类 A 要和类 B 对话。"** 如果开发者没提供有益描述、代码结构也不整洁，这类评论有助于推动设计清晰、代码更干净。
- **"看起来你打破了这里的接口边界。那会怎么影响用户？"** 你指出了注意到的问题，给了他们"本意如此"的推定。现在他们可以思考打破接口边界的那些不可见后果，要么为决定给出理由，要么选择改掉。

总体上，把反馈框成问题，是推动清晰、正确、同时帮开发者改进未来设计的好方法。这通常是高质量创意写作小组互相给反馈的方式。在创意写作情境里，说"我不喜欢这个角色"是有害的；而同样的话可以更清晰地重新表述："第一章里你的角色温暖而有同情心，现在他却冷漠如冰。在我眼里他不像真人。"现在有了可以被厘清、来排查问题的具体反馈。

程序员喜欢解决问题、指出问题，所以天性使然，他们喜欢发现和指出缺陷。很诱人的是，把代码评审当作"通过找同行代码里的问题来证明自己聪明"的方式。**别这么做。** 代码评审是让更多人看改动、排查关键问题的方式，但你的目标应该是：以鼓励团队成员"在解决眼前问题的同时提升技能"的方式去评审。

## 风格问题

花括号位置、变量/函数名、缩进和空格问题应当处理，但它们不是好代码评审的核心目的（注意我把它们放在代码评审金字塔顶端）。如果你发现团队 90% 的时间都在吹毛求疵地抠缩进和变量名，你很可能在"本可基本自动化"的事情上浪费所有人的时间。写一份风格指南，在提交（check-in）时强制缩进和空格问题，把时间花在更高价值的问题上。我无意贬低一致风格的重要性。正相反，拥有一致的、惯用的风格，是让代码库易于阅读和理解的最简单方式之一。但如果你把全部代码评审都花在这些简单任务上，问问自己：你是否在回避"让团队思想对齐、思考更高层设计"这个更艰难、更重要的职责。
