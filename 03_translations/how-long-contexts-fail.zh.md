# 长上下文为何失效（How Long Contexts Fail）

> 来源：dbreunig.com（2025-06-22），课程 Week 3 阅读 ｜ 副标题：管理好你的上下文，是智能体成功的关键

随着前沿模型的上下文窗口持续增长（许多已支持多达 100 万 token），我看到很多关于"长上下文窗口将解锁我们梦寐以求的智能体"的热烈讨论。毕竟，只要窗口够大，你就可以把可能需要的一切——工具、文档、指令等等——统统塞进提示词，然后让模型搞定其余。

长上下文曾给 RAG 的热情泼了冷水（都能全塞进提示词了，何必再找最好的文档？）、点燃了 MCP 的热潮（连接所有工具，模型什么活都能干！）、也助长了人们对智能体的热情。

但现实中，**更长的上下文并不会产生更好的响应**。过载你的上下文可能让你的智能体和应用以惊人的方式失效。上下文可能被污染、分散注意力、令人困惑、或相互冲突。这对智能体尤其成问题，因为智能体依赖上下文来收集信息、综合发现并协调行动。

我们来看看上下文失控的几种方式，再回顾缓解或完全避免"上下文失效"的方法。

## 上下文失效（Context Fails）

- **上下文污染（Context Poisoning）**：当幻觉混进了上下文
- **上下文干扰（Context Distraction）**：当上下文压倒了训练所学
- **上下文混淆（Context Confusion）**：当多余上下文影响了响应
- **上下文冲突（Context Clash）**：当上下文各部分彼此矛盾

### 上下文污染

上下文污染，是指幻觉或其他错误混进上下文，并被反复引用。DeepMind 团队在 Gemini 2.5 技术报告里点名了上下文污染（我们上周拆解过）。玩 Pokémon 时，Gemini 智能体偶尔会在游戏过程中产生幻觉，污染了它的上下文：

> 这个问题尤其恶劣的形式可能发生在"上下文污染"中——上下文的许多部分（目标、摘要）被关于游戏状态的错误信息"污染"，往往需要很长时间才能消除。结果，模型可能执着于实现不可能或无关的目标。

如果它上下文的"目标"部分被污染，智能体就会发展出荒谬的策略、反复重复行为，去追求一个根本无法实现的目标。

### 上下文干扰

上下文干扰，是指上下文变得过长，模型过度聚焦上下文、而忽视训练中学到的东西。在智能体工作流中，随着模型收集更多信息、积累历史，上下文不断增长，这种累积的上下文可能变得干扰而非有帮助。玩 Pokémon 的 Gemini 智能体清楚展示了这个问题：

> 虽然 Gemini 2.5 Pro 支持 100 万+ token 的上下文，但为智能体有效使用它构成了新的研究前沿。在这种智能体配置下，我们观察到：当上下文显著超过 100k token 时，智能体倾向于偏好从其庞大历史中重复动作，而非综合出新的计划。这一现象虽然只是轶事，却凸显了"用于检索的长上下文"与"用于多步生成式推理的长上下文"之间的重要区别。

模型不是用训练所学去制定新策略，而是执着于从它庞大的上下文历史中重复过去的动作。

对较小的模型，干扰上限低得多。一项 Databricks 研究发现，Llama 3.1 405b 的模型正确率在约 32k 处开始下降，更小的模型下降得更早。

如果模型远在填满上下文窗口之前就开始失常，那超大上下文窗口还有什么意义？简而言之：**摘要（summarization）和事实检索（fact retrieval）**。如果你做的不是这两件事之一，就要当心所选模型的干扰上限。

### 上下文混淆

上下文混淆，是指模型用上下文里的多余内容生成了低质量响应。有一阵子，看起来人人都要上线一个 MCP。那个"强大模型连接你所有服务和事物、替你干完所有琐事"的梦，仿佛近在咫尺。只要把所有工具描述塞进提示词、按一下开始。Claude 的系统提示词给我们指了路——它大部分是工具定义或使用工具的指令。

但即使整合与竞争不拖慢 MCP，上下文混淆也会。事实证明，**工具可能多到反而坏事**。

Berkeley 函数调用排行榜（Function-Calling Leaderboard）是一个评估"模型有效使用工具响应提示词"能力的工具使用基准。如今已到第 3 版，排行榜显示：**当提供超过一个工具时，每个模型的表现都变差**。而且 Berkeley 团队"设计了所有提供的函数都不相关的场景……我们预期模型输出为不调用函数"。然而，所有模型仍偶尔会调用不相关的工具。

看这个函数调用排行榜，你会看到模型越小、问题越严重。上下文混淆的一个突出例子来自一篇近期论文：它评估小模型在 GeoEngine 基准（一个包含 46 个不同工具的测试）上的表现。当团队给一个量化（压缩）的 Llama 3.1 8b 一个带全部 46 个工具的查询时，它失败了——尽管上下文远在 16k 上下文窗口之内。但当他们只给模型 19 个工具时，它成功了。

问题在于：**如果你把某样东西放进上下文，模型就不得不注意它**。它可能是无关信息或无谓的工具定义，但模型会把它考虑进去。大模型、尤其是推理模型，越来越擅长忽略或丢弃多余上下文，但我们仍不断看到无价值信息绊倒智能体。更长的上下文让我们能塞进更多信息，但这种能力伴随着副作用。

### 上下文冲突

上下文冲突，是指你在上下文里累积的新信息和工具，与上下文里的其他信息相冲突。这是上下文混淆一个更棘手的版本：这里的坏上下文不是"无关"，而是**直接与提示词里其他信息矛盾**。

一个 Microsoft 与 Salesforce 的团队在近期论文中精彩记录了这一点。该团队从多个基准取提示词，并把信息"分片（sharded）"到多个提示词中。这样理解：有时你会坐下来，在按回车前把整段整段的话敲进 ChatGPT 或 Claude，把所有必要细节都考虑到；另一些时候，你可能从一个简单提示词开始，当聊天机器人的回答不满意时再补充细节。Microsoft/Salesforce 团队把基准提示词改造成这种多步对话的样子——左边提示词里的所有信息被拆进右边多轮消息中，在多轮对话中逐步展开。

**分片提示词的结果大幅变差，平均下降 39%**。该团队测试了多种模型——OpenAI 备受推崇的 o3，得分从 98.1 跌到 64.1。

怎么回事？为什么信息分阶段收集、而不是一次给全，模型的表现反而更差？答案是**上下文混淆**：组装起来的上下文包含了整个聊天对话，其中含有模型在还没掌握全部信息时、就过早尝试作答的早期尝试。这些错误答案仍留在上下文里，在模型生成最终答案时影响它。该团队写道：

> 我们发现，LLM 经常在早期轮次做假设，并过早地尝试生成最终方案，且过度依赖这些方案。简单说，我们发现当 LLM 在对话中走错一步，它们就会迷路、无法恢复。

这对智能体构建者不是好兆头。智能体从文档、工具调用、以及被指派子问题的其他模型那里组装上下文。所有这些来自不同来源的上下文，有自我矛盾的可能。而且当你连接并非自己创建的 MCP 工具时，它们的描述和指令与提示词其余部分冲突的概率更大。

## 结尾

百万 token 上下文窗口的到来曾让人觉得是变革性的。"把所有智能体可能需要的东西塞进提示词"的能力，启发了"超级智能助手能访问任何文档、连接所有工具、保持完美记忆"的愿景。

但如我们所看到的，更大的上下文也创造了新的失效模式。上下文污染嵌入错误并随时间叠加；上下文干扰让智能体过度依赖上下文、重复过去动作而非向前推进；上下文混淆导致不相关工具或文档的使用；上下文冲突制造内部矛盾、扰乱推理。

这些失效对智能体打击最大，因为智能体恰恰在"上下文膨胀"的场景中运行：从多个来源收集信息、做连续工具调用、进行多轮推理、累积庞大历史。

幸运的是，有解决方案！我们将在后续文章中介绍缓解或避免这些问题的技术——从动态加载工具的方法，到建立"上下文隔离区"。
