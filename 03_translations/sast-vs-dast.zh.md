# SAST vs. DAST vs. RASP：应用安全测试方法对比

> 来源：Splunk 博客（2024-12-18，Shanika Wickramasinghe），课程 Week 8 阅读

全球信息安全支出预计到 2025 年将达 **2120 亿美元**，较 2024 年增长 15%。据 Gartner，生成式 AI 的兴起与云采用是快速增长的关键原因。该分析机构进一步预测，到 2027 年生成式 AI 将参与 17% 的网络攻击。企业需要超越传统方法的高级安全策略来应对这些日益增长的威胁。因此企业主需要了解 SAST、DAST、RASP 这类安全方案，它们为应用提供多层防护。

## 什么是 SAST？

**静态应用安全测试（Static Application Security Testing, SAST）**是一种白盒（white-box）安全测试方法。SAST 使用应用的静态源代码或二进制来识别漏洞——这意味着 SAST 工具在应用**不运行**时对应用代码进行操作。开发者用 SAST 检测各种安全风险，如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中其他 OWASP 漏洞。由于单靠 SAST 无法识别运行时特有的漏洞，开发者常需把 SAST 与其他测试方法结合，以获得全面安全。

SAST 是软件开发生命周期的重要组成部分，因为它**早期**检测漏洞。越早发现，修复成本越低。由于 SAST 工具可在开发阶段执行，开发者现在能写出代码并测试它——哪怕在发布到市场前测上千次（！）。

SAST 可集成进 CI/CD 流水线，此时被称为"安全 DevOps"或"DevSecOps"。SAST 通过自动化可广泛扩展。实现覆盖 SAST 技术的自动化测试，使其成为快速解决代码级风险的有效方案。

## 什么是 DAST？

**动态应用安全测试（Dynamic Application Security Testing, DAST）**是一种黑盒（black-box）测试方法。"Dynamic"一词表明该方法在应用**运行时**评估其安全性。与 SAST 不同，DAST 不需要访问应用源代码，而是：
- 模拟外部攻击者的行为；
- 从外部测试应用，识别仅运行时才出现的漏洞。

DAST 能识别各类安全缺陷，如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模仿真实世界的攻击场景，DAST 工具评估应用对模拟威胁的响应。用这种方法，开发者能识别出 SAST 等静态方法可能漏掉的弱点。通常，开发者在软件开发生命周期的后期执行 DAST，往往就在部署前。通过在真实环境中测试应用，DAST 提供运行时安全的清晰概览，并支持更好的、能抵御潜在攻击的应用。

## SAST 如何工作？

开发者用 SAST 工具应用预定义规则和其他检测方法——如模式匹配和数据流分析——来识别编码错误和其他漏洞。他们把这些工具集成进 IDE 或 CI/CD 流水线，在编码和测试阶段自动化扫描。

### 常见 SAST 方法

- **模式匹配**：扫描代码库，查找不安全编码实践的已知模式。例如使用弱加密算法或不安全的 API 调用。
- **数据流分析**：跟踪数据如何在应用中流动。通过把不受信任的输入路径追溯到敏感操作，可识别 SQL 注入或缓冲区溢出等漏洞。
- **控制流分析**：分析应用的控制结构，如循环和条件，以发现逻辑缺陷或竞态条件等潜在漏洞。
- **自定义规则创建**：许多工具允许开发者创建自定义规则以落实编码最佳实践。示例：标记 SQL 查询中任何未净化输入的使用；识别未经正确转义就把用户提供数据输出到浏览器的代码；高亮 eval()（JavaScript）或 strcpy()（C）等易受攻击或已废弃函数的使用；检测源码中硬编码的 API 密钥和密码、标记任何缺少输入验证的用户数据实例。
- **依赖扫描**：有些 SAST 工具分析应用使用的第三方库和框架，以识别依赖中的漏洞。
- **语义分析**：通过解读代码的含义（而非仅结构），SAST 工具可检测不安全配置或 API 误用。
- **机器学习模型**：高级 SAST 工具引入机器学习算法，通过分析跨大型数据集中的模式来识别此前未知的漏洞。

### 使用 SAST 工具的性能考量

SAST 工具常需要大量 CPU 和内存资源。分析大型代码库时这可能成为大问题——对一百万行代码做全量扫描可能消耗数 GB 内存。SAST 扫描所需时间随代码库大小差异很大，从小项目的几分钟到企业应用的数小时。这可能影响：构建流水线时间线、开发者生产力。可考虑使用支持**增量扫描**的现代 SAST 工具，只分析变更的代码而非整个代码库。此外，通过规则选择和范围界定做性能调优至关重要。配置不当的 SAST 工具可能不必要地分析非关键代码路径，浪费时间和资源却无安全收益。

## DAST 如何工作？

DAST 工具模拟真实攻击——例如把各种恶意数据发送进输入字段，看应用如何处理它——来识别应用行为与响应中的漏洞和弱点。

### DAST 的步骤

**第 1 步：扫描。** 扫描 Web 应用以发现入口点（如 URL、表单和 API）。这步绘制应用结构、识别潜在攻击面。
**第 2 步：攻击模拟。** 通过向应用发送精心构造的请求来模拟恶意活动。这些请求通过尝试利用入口点，测试跨站脚本和跨站请求伪造等漏洞。
**第 3 步：漏洞检测。** 分析应用的响应以识别安全弱点。它评估应用在攻击下是否如预期行为。例如可注入恶意数据以检测 SQL 注入缺陷。
**第 4 步：报告。** 生成带检测到的漏洞和补救建议的报告。开发者可用报告中的结果修复已识别问题。

现代 DAST 方案可融入 AI 驱动分析和实时数据集成等高级功能，自动创建测试集、动态适配应用结构、用机器学习算法最小化误报。

### 使用 DAST 工具的性能考量

使用 DAST 工具有几个性能瓶颈要留意：
- DAST 工具与应用互动，临时增加应用和 Web 服务器的 CPU 与内存占用；
- DAST 扫描期间产生的高并发请求会消耗大量网络带宽；
- DAST 扫描器常通过生成唯一请求来绕过或使应用缓存失效，降低缓存机制有效性；
- DAST 工具创建和管理多个测试会话会增加应用服务器的内存占用。

为尽可能避免或降低影响，遵循以下实践：在应用使用最少的非高峰时段安排 DAST 扫描；在镜像生产配置的预发布（staging）或预生产环境执行扫描；用 DAST 工具的限流功能控制并发请求数；扫描期间增加应用服务器线程池；为 DAST 扫描器 IP 配置独立的缓存策略；若性能超限，实现自动挂起扫描。

## SAST vs. DAST：关键差异

| 标准 | SAST | DAST |
|---|---|---|
| 测试类型 | 白盒测试。可访问源代码，从内到外测试应用。 | 黑盒测试。不访问源代码，从外测试应用。 |
| 支持的软件类型 | 支持多种软件，包括 Web 应用、Web 服务和厚客户端。 | 支持 Web 应用和 Web 服务，通常不支持其他软件类型。 |
| SDLC 阶段 | 在开发生命周期早期执行。 | 在 SDLC 后期执行，常在部署期间或之后。 |
| 检测的漏洞 | 识别编码缺陷，如 SQL 注入、XSS、缓冲区溢出等。 | 检测运行时问题，如服务器配置错误、DoS 漏洞和应用级缺陷。 |
| 修复成本 | 因在 SDLC 早期识别，成本较低。 | 因漏洞发现较晚、常需紧急修复以按时部署，成本较高。 |
| 运行时与环境问题 | 无法检测运行时特有或环境相关漏洞。 | 能识别仅运行时或因环境因素出现的漏洞。 |
| 深度 vs. 广度 | 对代码级漏洞提供深入洞察。 | 对外部安全风险提供广泛视角。 |
| 工具集成 | 集成 IDE 和 CI/CD 流水线，做自动化静态分析。 | 集成 CI/CD 流水线，做持续运行时测试。 |
| 误报与漏报 | 因深度代码分析，误报概率更高。 | 误报较低，但内部可见性有限，漏报风险更高。 |
| 技术依赖 | 依赖编程语言和框架，需要与工具兼容。 | 独立于应用框架，因为从外部与应用交互。 |

## SAST 与 DAST 的优缺点

### SAST 的优点
- 在开发生命周期早期识别安全漏洞；
- 分析代码库，包括基础函数和复杂分支；
- 直接对源代码操作，无需应用运行；
- 提供带全面洞察的实时反馈，如漏洞的精确位置；
- 生成可用仪表盘跟踪的可导出报告；
- 支持自动化，比人工代码评审更快、更高效。

### SAST 的缺点
- 常产生大量误报，可能需要人工复核；
- 无法识别运行时或环境特有漏洞，如配置错误；
- 需要每种编程语言对应的工具，维护复杂；
- 难以理解外部库、API 和 REST 端点。

### DAST 的优点
- 识别仅应用执行期间才出现的漏洞；
- 外部操作、无需访问源代码，对测试第三方应用或编译代码有效；
- 模拟真实攻击场景，识别 SAST 漏掉的风险；
- 独立于应用编程语言；
- 评估整个应用和系统，包括内存消耗、资源使用和第三方接口。

### DAST 的缺点
- 只聚焦应用外层，可能漏掉更深层漏洞；
- 在 SDLC 后期应用，修复更贵、更耗时；
- 会漏掉 SAST 通过源码分析能识别的某些漏洞。例如，一个 Web 应用用不安全的随机数生成器（如 JavaScript 的 Math.random()）创建会话 token，DAST 可能漏掉它（因为它只测运行时行为），而 SAST 能检测到；
- 大型项目需要自定义基础设施和多个应用实例并行运行，因此资源密集。

## 什么时候该用 SAST 还是 DAST？

SAST 和 DAST 在保护 SDLC 上互为补充。理解何时用哪个，有助于获得全面安全覆盖。

### 何时用 SAST
- **早期开发阶段**：开发者用 SAST 在 SDLC 早期识别 SQL 注入和硬编码凭据等漏洞。在部署前抓住它们，降低修复成本和复杂度。例：SAST 工具扫描 Python 代码，标记源码中硬编码 API 密钥的漏洞；开发者重构代码改用环境变量安全存储和取回密钥。
- **代码评审**：SAST 集成进版本控制系统，允许开发者在提交前扫描代码，确保只有安全代码进入仓库。例：SAST 工具检测"文件路径直接由用户输入构造且未验证、暴露路径遍历攻击"的漏洞；开发者通过净化输入、用安全库函数处理文件路径来修复。
- **CI/CD 流水线**：SAST 在 CI/CD 过程中运行自动化扫描，给开发者实时反馈。

### 何时用 DAST
- **预生产测试**：开发者用 DAST 在预发布或 QA 环境识别运行时漏洞（如不安全配置、认证缺陷、访问控制不足）。例：DAST 工具检测暴露敏感数据的数据库配置错误；开发者随后在部署前加固配置。
- **部署后监控**：DAST 工具持续扫描已部署应用，寻找由环境变化或新兴威胁造成的漏洞，确保应用随时间保持安全。
- **测试第三方集成**：DAST 可模仿外部攻击者视角，识别第三方 API 或互联系统中的漏洞。例：DAST 工具测试 Web 应用，发现第三方支付 API 里信用卡数据正通过未加密的 HTTP 连接传输；开发者通过为所有 API 通信强制 HTTPS 解决。

## 哪个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：SDLC 阶段；要解决的漏洞类型。SAST 在早期开发中最佳，主要识别源代码漏洞、降低成本、促进安全编码实践。DAST 则聚焦预生产或已部署应用的运行时漏洞，提供对配置错误和不安全集成等问题的洞察。

### 采用混合方法
与其二选一，不如把 SAST 和 DAST 结合，创造一种多层安全策略，同时解决静态代码和运行时环境的漏洞。SAST 可集成进早期开发阶段，在应用编译前检测并修复代码级问题；应用在测试环境运行时，DAST 识别运行时漏洞、评估应用在攻击条件下的行为。在 CI/CD 流水线中自动化 SAST 和 DAST 扫描，可提供持续反馈，并在不牺牲安全的前提下加速开发。对敏捷或 DevOps 环境，加入 IAST 或 RASP 等工具可进一步增强安全。通过关联 SAST 和 DAST 的结果，组织能实现更全面、更有效的漏洞管理。

### 用 RASP 作为 SAST 和 DAST 的替代
**运行时应用自我保护（Runtime Application Self-Protection, RASP）**是一种直接安装在应用运行服务器上的高级安全方案。RASP 把自己嵌入应用的运行时环境，从而能分析应用的逻辑和数据。分析时可：实时检测异常行为；即时阻断恶意活动。一个关键区别是，RASP 不仅对潜在问题告警——它主动防止攻击，通过隔离和解决威胁、而无需依赖外部工具。RASP 提供 SAST 和 DAST 的动态替代方案。与"SAST 分析静态代码、DAST 模拟外部攻击"不同，RASP 实时操作：监控应用执行期间的行为，通过终止会话或告警防御者来响应实时威胁。RASP 在保护"绕过网络防御或在开发期间被漏掉"的漏洞上特别有效。然而，对 RASP 的过度自信会让组织忽视安全编码实践。此外，因直接运行在应用运行时环境内，RASP 可能影响应用性能。RASP 不能替代修复底层缺陷的需要，但它在修复进行期间提供持续保护。正如一位 RASP 用户评论："是否使用 RASP 工具，应基于对应用特定需求和风险画像的彻底评估。"

## 未来是 SAST、DAST 与 RASP 结合的应用安全测试

应用测试的未来在于结合 SAST、DAST 和 RASP，创建全面的安全策略。随着安全挑战增长，把这些工具集成进 CI/CD 流水线并自动化其流程将变得必不可少。AI 和机器学习的进步将使测试更高效——帮助减少误报、改善威胁检测。

**金融与金融服务行业**：在金融领域，AI 驱动工具将转变漏洞被检测和缓解的方式。SAST 和 DAST 将继续在开发和预生产阶段识别编码缺陷和运行时问题。而 RASP 会走得更远，用 AI 监控实时交易。例如 RASP 可检测异常模式（如攻击者实时尝试利用漏洞）并阻断这些活动、同时通知安全团队。

**IoT、边缘与联网设备**：对 IoT，这些工具的组合将在保护联网设备上扮演重要角色：SAST 在开发期间确认固件没有漏洞；DAST 测试设备间通信协议的安全性；RASP 则监控已部署设备，检测并阻止新兴威胁造成的未授权访问尝试或数据泄露。同样，使用多种方法将帮助 IoT 生态系统保持韧性。如我们许多例子所解释的，SAST、DAST 和 RASP 共同承诺一个"应用以更强、更主动的安全措施被构建和部署"的未来。

## 韧性安全始于主动测试

把 SAST、DAST 和 RASP 结合，可提供覆盖整个软件开发生命周期的稳健安全。通过把这些方法集成进 CI/CD 流水线并利用 AI 进步，组织能主动响应新兴威胁。这些方法共同为"保护现代应用免受安全漏洞"提供了整体性方法。
