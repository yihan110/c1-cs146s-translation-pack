# 拿说明 ④ · 34 篇译文的机器抽检：怎么证明"没有漏译/机翻硬伤"

> 这是 contentAccuracy + aiUsage 的闭环证据：覆盖度 100% 只是"每篇都有译文文件"，不代表译得对。我加了一道机器抽检脚本，把"人肉觉得没问题"变成可复跑的数字。

## 问题
前三个闸门（术语一致、覆盖度）只回答"术语对不对、有没有文件"。它们**回答不了**：译文里有没有大段英文没翻？有没有哪篇其实是占位却报了完成？这类问题靠通读 34 篇约 9.5 万字不可靠，也不可复跑。

## 我写的抽检脚本（04_pipeline/05_qa_sample.py）
做两件事：
1. **数中文字符**：逐篇统计 CJK 汉字数，找出"文件不小但汉字极少"的疑似占位篇；
2. **抓残留英文长句**：剥掉代码块后，正则找译文里"连续 ≥6 个英文词的完整句"——这类最像漏译。

给脚本的指令（即"prompt"）：
```
对 03_translations/*.zh.md：
- 统计每篇汉字数（[\u4e00-\u9fff]）；
- 剥掉 ``` 代码块和 `行内代码` 后，抓 >6 词的英文长句；
- 列出汉字 <200 且文件 >200 字节的篇；
- 输出 05_quality/qa_sample_report.json。
```

## 跑出来的结果（真实数据）
- 全包汉字总数：**94,702**（≈9.5 万，与 README 自报一致）；
- 疑似低汉字篇：**仅 3 篇**——`good-context-good-code` / `how-warp-uses-warp` / `peeking-under-the-hood`，正是那 3 个 JS 空壳/被墙占位页（原文 <30 词，本就无正文可译），不是漏译；
- 残留英文长句命中 2 篇：`how-openai-uses-codex`、`prompt-engineering-overview`。

## 关键一步：机器报警后，人来判定（不盲信脚本）
脚本报"残留英文"后我没有直接当漏译修，而是打开这两篇核对：命中的句子是——
> "Where is the authentication logic implemented in this repo?"
> "Split this file into separate modules by concern and generate tests for each one."

这些是**文章里给读者的示例 prompt**。按翻译规则"示例 prompt / 代码 / 命令保留英文原文"，它们**应当保留英文**，是正确处理，不是漏译。脚本把它们列为"待人工确认"而非"错误"，正好证明闸门会报警、但不冤枉。

## 对比
| 做法 | 结果 |
|---|---|
| 不做抽检，直接交 | "无漏译"只是口头主张，评审无从复核，contentAccuracy 丢分 |
| 写抽检脚本但见英文就翻 | 会把正确保留的示例 prompt 也翻译成中文，破坏规则 |
| **脚本报警 + 人工逐案判定 + 区分"漏译/应保留"** | 94,702 汉字可复核，3 个占位篇有据，2 处报警经判定为正确保留 ✅ |

**核心方法**：质量闸门要能"报警"，但判定权在人——脚本负责把可疑项捞出来，人负责区分真漏译和该保留的内容，并把判定理由写进报告。
